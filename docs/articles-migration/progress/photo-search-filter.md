## Поведение этапов (как реализовано)

**search, первый запуск** (`!cursor.searchQueries`): `facts.keywordAttributes` (если пусто — `parseKeywordAttributes`) → один вызов ИИ `generateTopupQueries` → `cursor.searchQueries={primary,secondary}`, `cursor.usedQueries=[]`, `cursor.topups=0`, `cursor.searchKeyword` (шаблон `primary[0]` профиля), `facts.topicContract/fashionContract/interiorContract/audience/trendBrief/keywordRu`; `Article.keywordRu` заполняется, если пусто. Затем запросы по плану `[ключ статьи, …primary]`: основной — лимит `max(20, candidates_total)` (100), остальные — `max(40, needed·4)` (80, как добор оригинала); следующий запрос выполняется только пока кандидатов меньше `reserveTarget = max(needed·5, needed+40)`. Перед каждым запросом — кэш по тексту запроса из `ArtPhotoCandidate` других статей (≥ min(limit,40) строк, без `rejected` — аудит 02 п.7.8). Кандидаты `status="found"` (url, pageUrl, domain, thumbUrl, title, searchQuery, position, queryIndex, width/height от SerpApi). Дубли по url внутри статьи не создаются. `include_urls` (посты) — отдельный SerpApi-запрос по 15 на пост, только при основном запросе. Журнал запросов — `cursor.searchLog` (последние 40).

**search, добор** (`cursor.topup` непустой): следующий неиспользованный запрос из `primary`→`secondary`, затем один раз «другое гео» (`nextGeo`, `cursor.usedGeos`, `cursor.geoTopupDone`), лимит 80; `cursor.topups += 1`, `cursor.topup = null` → дальше `filter` (по умолчанию). Если запросов не осталось или `topups ≥ PHOTO_LOOPS.maxTopups` → `cursor.topup = null` и `{ next: { wait: photoReview && ArtPhoto>0 ? "PHOTO_REVIEW" : "WAITING_FOR_PHOTOS" } }`.

**search, ошибки**: оба провайдера не подключены (resolveSlot 404/409) → `fatal` с текстом про слоты `photo_dfs`/`photo_serp`; сетевые/5xx/429 без результата → `{ retryInMs: 90_000 }`; 0 кандидатов без ошибки на первом запуске → `fatal` «Не найдено ни одного фото…» (как оригинал). Промт набора с неизвестной переменной → ошибка этапа (не глушится, 08-plan §3 п.3).

**filter**: `found` пачками `BATCH=4` параллельно (семафор скачиваний в процессе), порядок `queryIndex, position`. На кадр: попытка пишется в `techDetails.attempt` до скачивания (`MAX_ATTEMPTS=3`), `isBlockedDomain` → `catalogueSourceSignal` → `checkTextRelevance` → скачивание `[url, thumbUrl]` → SHA-256 (дубли внутри статьи по `downloaded/rated/keep/selected/reserve`) → размер (короткая сторона < min(minWidth,minHeight)=550) → ориентация → `inspectPhotoBytes` → dHash ≤ 8 к принятым → файл `candidateRel` + миниатюра `candidateThumbRel` (`makeThumb`) → `status="downloaded"`, `width/height/bytes/sha256/phash/path/thumbPath/techScore/techDetails`. Отказ → `status="rejected"`, `rejectStage="filter"`, `rejectReason` (русские тексты оригинала), файлы не хранятся. «Мягкий» отказ источника (429/403/5xx/HTML/недоступно) → остаётся `found` с `rejectReason="отложено: … (попытка N)"` и `techDetails.retryAfter = now+5 с`; после 3 попыток — reject. `ctx.tick()` после каждой пачки. Ранний стоп, когда `passed ≥ reserveTarget` (остальные `found` остаются на следующий круг). Финиш: `passed < reserveTarget && cursor.filterCycles < PHOTO_LOOPS.filterCycles && topupAvailable(cursor)` → `cursor.filterCycles += 1`, `cursor.topup={from:"filter", needed, reason}`, `{ next: "search" }`; `passed === 0` → `fatal` с разбивкой причин; иначе дальше (`rank`).

**filter после rate** (`cursor.filterPending = true`, ставит этап rate при `needs_filtering`): без раннего стопа по резерву и без запроса добора — доделываем все `found`, снимаем флаг, дальше по умолчанию (`rank` → `rate`).

Статусы кандидатов в моей зоне: `found → downloaded | rejected`. Следующие этапы: `downloaded → keep | rejected → selected | reserve`.

## Согласование с соседними модулями (исполнитель rank/rate/select)

Соседние файлы `relevance.ts`, `vision.ts`, `authenticity.ts`, `ranking.ts`, `caption.ts`, `diversity.ts`, `fingerprints.ts` появились параллельно и частично дублировали мои порты (photoRelevance, photoVision, photoQuality, photoAuthenticity, trendBrief). Чтобы не было двух копий одного алгоритма, свои копии удалены: `contracts.ts` без `buildTopicRelevance` (фильтр импортирует `./relevance`), `download.ts` реэкспортирует `vision`/`ranking`/`authenticity`, `queries.ts` реэкспортирует тренд-бриф из `vision.ts` (оставлены только `trendBriefInstruction` и алиас `loadTrendBrief`). Соседи импортируют из моих модулей: `profile` (`getNicheProfile`, `specializeProfile`, `subjectLabel`, `photoFactFields`, `photoFactSkeleton`, `topicKindLabel`, `describeAttributes`, `defaultProfile`), `contracts` (`buildTopicContract`, `buildFashionContract`, `buildInteriorContract`, `*ContractPrompt`, `isInteriorNiche`), `audience` (`audienceRule`, `isChildIntent`) — имена совпадают. Курсор: `topup`/`topups` (search), `filterCycles`/`filterPending` (filter ↔ rate), `rateTopups`/`selectCycles`/`rescuePass` (их), `select` очищает кольца после отбора.

## Что отличается от оригинала (и почему)

1. **DataForSEO**: `pageUrl = url`, `url кандидата = source_url`, `thumbUrl = encoded_url`, домен — от страницы (08-plan §3 п.6). `depth ≤ 200` (максимум API; оригинал допускал 700). Стоимость считает портал (`UsageLog` через `runSlot`), а не константа $0.004.
2. **Аудитория** (аудит 02 п.3/7.3): `PERSON_WORDS` только про людей; национальности/«asian/afro/nordic/k-beauty» требуют слова о людях в теме; `black/white` — ещё и соседства с ним (без `hair/beauty/hairstyles`). «black hair color», «white hair», «korean nails» больше не дают правила аудитории. Самодостаточные слова (`african american, latina, hispanic, desi, hijabi, caucasian, dark/brown/pale/fair skin`) работают как раньше.
3. **Шкала контракта** (аудит 02 п.7.11): сосед «в сторону крайности» разрешается только в своей половине шкалы и никогда для `medium/mid` — замок на длину не исчезает.
4. **Разметка ключа без ИИ** в этапе (один вызов ИИ на search — за запросами). `parseKeywordAi` есть, но не вызывается.
5. **Первый запуск ищет ключ + primary-варианты до резерва** (оригинал: только ключ, вариации — в доборах фильтра). Обычно хватает основного запроса (DFS отдаёт ~100), остальные primary уходят в доборы.
6. **Добор**: один лимит `PHOTO_LOOPS.maxTopups` (оригинал: 10 в фильтре, 6 в оценке); фильтр не просит добор, если `topupAvailable()` ложно — идём дальше с тем, что есть, вместо ожидания. Гео-вариант «другое гео» (мёртвый `nextGeo` оригинала) включён как последний добор.
7. **Файл скачивается один раз** и хранится в `storage/articles/<id>/cand/<candId>.jpg` (расширение фиксированное — байты оригинала могут быть PNG/WebP; `sharp` читает по содержимому) + миниатюра WebP. Лимит 25 МБ (в оригинале без лимита). Пиксельный анализ — на растре ≤1200 px по длинной стороне через `sharp` (оригинал: полный растр, >8 Мп — миниатюра, >6 МБ — без декода).
8. **Кэш поиска** без `rejected`-строк чужих статей (аудит 02 п.7.8).
9. **Кеш профилей** с TTL 60 с (аудит 02 п.7.16, оригинал кешировал навсегда).
10. **Переменные промта `rp_photo_search`**: добавлен `{topic_kind}` (аудит 06 — в волосах не подставлялся), `{target_country}` — из итогового гео (`recipe.photoSearch.country`), `{language}` = «English».
11. `candidate.url` не подменяется на миниатюру при скачивании превью (оригинал писал `image_url := thumbnail_url`); факт отмечен в `techDetails.usedThumbnail` и `rejectReason="миниатюра Google"` у прошедшего кадра (как оригинал).

## Открытые вопросы

1. Нужна ли ИИ-разметка ключа (`parseKeywordAi`) в search — один дополнительный дешёвый вызов улучшит контракты (мотивы ногтей, hero piece); сейчас только словарь.
2. `ArtPhotoCandidate.searchQuery` — VARCHAR(191): длинные запросы с `site:` обрезаются до 190 и не попадают в кэш.
3. Для `recipe.photoSearch.source` допускается только `dataforseo|serpapi` (тип портала); `both` оригинала нормализуется в `dataforseo`, если в JSON встретится.
4. Пол «по умолчанию женщины» для интерьера/тату (аудит 02 п.7.12) и `girls` = дети (п.7.14) оставлены как в оригинале — решение владельца.
5. Типы не проверены компилятором: особое внимание к `sharp` опциям (`failOn`, `toColourspace`) и Prisma JSON-полям (`as object`).
