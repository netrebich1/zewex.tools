# План переноса сервиса «Статьи» (Pinterest Articles)

Опирается на отчёты 01–07. Что здесь решено — исполняется в коде; спорное помечено «решение».

## 1. Архитектура в zewex.tools

- **Проект** `articles` в разделе Pinterest, страницы `/pinterest/articles/*`, модели Prisma с префиксом `Art` (статья — `Article`).
- **Статья = строка очереди.** Нет отдельной таблицы задач: `Article.status/stage/cursor/leaseUntil/workerId` (как `DomainRun`). Один захват = одна статья, воркер гонит её по этапам подряд до состояния ожидания (модерация фото, модерация статьи) или конца. Лимиты: глобальный `ARTICLES_WORKER_CONCURRENCY`, на сайт — две цепочки «фото» и «написание» с выключателями и лимитами в настройках сайта (как в оригинале `auto_photo_enabled`/`auto_writing_enabled`, `max_photo/writing_concurrent`).
- **Этапы** (`src/lib/articles/stages.ts`), ключи реестра совпадают с оригиналом:
  - real_photo: `search`(11) → `filter`(12) → `rank`(125) → `rate`(13) → `select`(14) → ⏸ `PHOTO_REVIEW` (если включена модерация фото до текста) → `plan`(15) → `section_plan`(16) → `blueprint`(65) → `intro_outro`(72) → `sections`(73) → `meta`(77) → `assemble`(76) → ⏸ `REVIEW_PENDING` (если публикация не авто) → `publish`(78) → `COMPLETED`.
  - generated_photo (волна 3): `concept`(2) → `images`(5) → `image_seo`(6) → `blueprint` → … как выше.
  - Откаты «назад» (добор фото 13→12, 65→позиции) — внутри одного прохода, курсор в `Article.cursor`.
- **Промты и модели — как есть.** `ArtPromptSet`/`ArtPrompt` со старыми UUID; `ArtRecipe` (= сценарий) хранит `stagePromptIds`, `stageModels` (`provider:model`), `photoSearch`, `text`, `images`, `publish`. Резолвинг промта: рецепт → активный набор по нише/формату → `stagePromptIds[stage]` → первый вариант. Модель этапа: `stageModels[stage]` → модель правила слота портала.
- **Ключи — через портал.** Слоты проекта `articles`: `text_main` (писатель), `text_fast` (дешёвые шаги), `vision` (оценка/отбор фото), `image_main` (генерация), `photo_dfs` (DataForSEO), `photo_serp` (SerpAPI). `runSlot` получает необязательный `model` — если провайдер правила совпадает с префиксом `provider:` в рецепте, используется модель из рецепта, иначе модель правила (с предупреждением в журнале этапа).
- **Хранилище:** `storage/articles/<articleId>/cand/<candId>.jpg|.thumb.webp` и `storage/articles/<articleId>/photos/<pos>.jpg|.thumb.webp` → `/files/…`. Трансформации — `sharp`. Оригиналы кандидатов удаляются после отбора, фото статьи — после публикации с `wpUrl`.
- **Доступ:** сайт сервиса `ArtSite.accessId → SiteAccess`; видимость через `src/lib/sites/access.ts` (тот же механизм, что у Пинов). Статьи видны тем, кто видит сайт.
- **Расход:** `UsageLog.refId = articleId`; `Article.costUsd` пересчитывается после этапа. Авто-отключение ключа при 401/402 (уже есть в портале) заменяет `provider_billing_status`.
- **Ошибки:** `ArtStageLog` (каждый этап: начало/конец/ошибка/стоимость) и `ArtError` (сигнатура, статья, сайт, «устранено») — вместо триггеров БД.

## 3. Что исправляем при переносе (из аудита, без изменения смысла)

1. `{{section_brief}}` → `{{section_briefs}}` в наборе «Одежда · Реальные фото» (брифы секций не доходили до писателя).
2. `stage_7_intro_outro`: подставлять `outro_plan`/`care_plan` в вызове вступления, `content_angle`/`subcategories`/`trend_details` — в заключении (один промт, один набор переменных).
3. Один `fillVars`: `{{var}}` и `{var}` одинаково; остаток `{{…}}` после подстановки (кроме `{{COUNT}}`) — ошибка этапа, а не текст для модели.
4. `rp_photo_rate`: модель берётся из рецепта (`stageModels`), а не из `rating_model` конфига поиска.
5. Промо отклонённых кандидатов по `ai_score ≥ 6` — не для «жёстких» причин (каталог, ИИ, дети, не та аудитория).
6. DataForSEO: `pageUrl` = поле `url` (страница), `sourceUrl` = `source_url` (файл); подпись источника и домен-фильтры — по странице.
7. `normalizeSections`: номер секции берётся из ответа модели, пропуск = «недостающая», без сдвига текстов на чужие фото.
8. Пустые секции — не удалять молча; статья останавливается с понятной ошибкой.
9. Публикация: поиск поста по slug до создания, `wpPostId` сохраняется сразу после ответа WP; повтор не создаёт дубль.
10. Пароли WP и ключи — только зашифрованные (уже так в портале).
11. `min_width/min_height 450` в сценариях → 550 (так работал код).

Остальные находки аудита (≈60) — в отчётах; исправляются по ходу переноса соответствующего этапа.

## 4. Экраны (волна 1)

| Маршрут | Экран |
|---|---|
| `/pinterest/articles` | Обзор: сайты с воронкой статусов, воркер, ошибки за час; кнопки «Новый запуск», «Модерация фото (N)», «Модерация статей (N)» |
| `/pinterest/articles/sites` · `/sites/[id]` | Сайты сервиса; вкладки Очередь (фильтры, массовые действия) / Настройки (ниша, рецепт, фото, режим, публикация, категории WP, автозапуск и лимиты, ИИ-модерация, поиск по умолчанию) |
| `/pinterest/articles/runs/new` · `/runs/[id]` | Новый запуск по шагам (сайт → рецепт → ключи → параметры); карточка запуска |
| `/pinterest/articles/articles/[id]` | Карточка статьи: шапка, таймлайн этапов, вкладки Фото / Текст / Публикация / Журнал; повтор с этапа, стоп |
| `/pinterest/articles/moderation/photos` | Модерация фото (режим «фото до текста»): одна сетка «В статье» + «Резерв», клавиши, размеры, undo, «Мало фото», «Добрать» |
| `/pinterest/articles/moderation/articles` | Модерация статей перед публикацией: мета, фото с текстом секции, одобрить / опубликовать / в доработку |
| `/pinterest/articles/publications` | Ошибки / В очереди / Опубликовано; повтор |
| `/pinterest/articles/recipes` · `/recipes/[id]` | Рецепты: основное, промты по шагам с моделями и переменными, поиск фото, история версий |
| `/pinterest/articles/journal` | Ошибки (группы по сигнатуре, вернуть в работу) / Вызовы ИИ / Расходы |

Волна 2: ИИ-модерация, автозапуск-страница (пока — в настройках сайта), статистика сотрудников, Telegram, Google Sheets. Волна 3: generated_photo и визуальные промты.

## 5. Порядок работ

1. Схема Prisma + seed (ниши, профили, наборы, промты, рецепты, проект и слоты).
2. `src/lib/articles`: типы, реестр этапов, резолвер промтов, ИИ-клиент, доступ, хранилище, подписи статусов.
3. Воркер: очередь статей, раннер этапов, журнал.
4. Перенос этапов: фото-цепочка (02), текстовая цепочка (03), публикация (04) — параллельно, по отчётам и исходникам.
5. UI волны 1.
6. Проверка типов на сервере в копии, деплой, прогон одной статьи на тестовом сайте.
