# Расходы, волна 3 — правки A (п.2 «rank после rate» и п.3 «кэш промта Gemini»), 2026-10-16

Исходник наблюдений: `cost-notes-zorvianix.md`, раздел «Структура расходов, волна 3». Не задеплоено, не закоммичено.

## A. Сравнение кадров (rank) после оценки (rate)

Было: `search → filter → rank → rate → select`; rank сравнивал все ~130 прошедших фильтр кадров (13 vision-вызовов),
rate затем отклонял ~65 % из них; beautyRank использовался оценкой только как порядок пачек.
Стало: `search → filter → rate → rank → select` — rank сравнивает только одобренные оценкой (~42 кадра, 5–6 вызовов).

Что изменилось:
- `src/lib/articles/stages.ts` — порядок `REAL_PHOTO_STAGES`, описания этапов, пометка в шапке.
- `worker/articles/stages/rank.ts`:
  - кандидаты: `status in (keep, selected, reserve)` и `beautyRank IS NULL` (раньше — все `downloaded`); идемпотентность
    и логика групп/турнира чемпионов без изменений;
  - после записи `beautyRank` пересчитывается `rankScore` (`finalPhotoRank`) — оценка писала его без балла красоты;
  - защита для статей, заставших старый порядок на этапе `rank` (оценки ещё нет): если ни у одного кандидата нет
    `aiScore`, этап возвращает `{ next: "rate" }` (раннер поддерживает явный `StageKey`, как `next: "search"` в поиске),
    ставит `cursor.rankToRate = true`; после rate реестр ведёт статью снова в rank, флаг снимается. Второй раз подряд
    не отправляет — цикла rate → rank → rate быть не может. Сам rate после нормального завершения всегда оставляет
    оценённые кандидаты (иначе уходит к filter / search / WAITING_FOR_PHOTOS), так что в штатной работе защита не срабатывает.
  - тема статьи — первой строкой user, система без неё (см. раздел B; промт короче минимума кэша, но раскладка единая).
- `worker/articles/stages/rate.ts`: порядок пачек `techScore DESC, createdAt ASC` (NULL в конце) вместо `beautyRank DESC`;
  промо при нехватке (`promoteSoftRejects`) без изменений — промо-кадры получают статус keep без beautyRank, их сравнит rank.
- `worker/articles/stages/select.ts` — без изменений: `candidateRank` считает ранг по живым полям (null beautyRank →
  формула без красоты), резерв/промо работают как раньше.

Проверка раннера: `result.next` строкой → `next = result.next`, далее `prisma.article.update({stage: next})`; при ожидании
(`wait`) берётся `next ?? nextStage(...)`. Переход `rate → rank → select` линейный; обратно только из rank по защите (один раз)
и из rate/select к `filter`/`search` по прежним кольцам добора (при доборе после select цепочка снова `filter → rate → rank →
select`: rank сравнит только новые одобренные без beautyRank).

Состояние базы на 2026-10-16 (только чтение): статей со `stage='rank'` в очереди нет (в ожидании — 3 на `filter`, 6 на `plan`).

SQL «на всякий случай» после деплоя (НЕ обязателен благодаря защите; выполнять только при остановленном воркере и только для
ожидающих, не для RUNNING — у выполняющейся статьи раннер держит этап в памяти):
```sql
UPDATE Article SET stage='rate' WHERE stage='rank' AND status='PENDING';
```

Ожидание: −7…8 vision-вызовов rank на статью ≈ −$0.0025 (rank $0.0048 → ~$0.002), как в оценке волны 3.

## B. Кэш промта Gemini

### Что замерили (стенд: временный `scripts/articles/cache-probe.ts` в `/root/zewex-check`, прямой вызов OpenRouter с
`usage.include`, ключ из базы; реальный промт оценки ниши hair с промтом набора, 2 миниатюры; удалён после замера)

Неявный кэш (implicit, без `cache_control`):
| Раскладка | gemini-2.5-flash-lite | gemini-2.5-flash | gemini-3-flash-preview |
|---|---|---|---|
| Один системный текст: общий статичный префикс ~1.7k ток., дальше тема/тренд (как было, но статичное первым) — статья A → B | 0 % | 0 % | 0 % |
| То же, статичный префикс ×2 (~3.5k ток.) — A → B | 0 % | 0 % | 0 % |
| Система только статичная, всё про статью в user — A → B → C | 0 % | 0 % | 0 % |
| Полностью одинаковый запрос, повтор | 73 % (срабатывает нестабильно: на 2–4-м повторе) | 73 % (на 4-м повторе) | 66 % (один раз из пяти серий) |
| Одинаковый текст, другие фото | 0 % | — | — |

Вывод: через OpenRouter неявный кэш Gemini срабатывает только при ПОЛНОСТЬЮ одинаковом тексте до картинок и после
2–3 повторов; общий префикс внутри системного сообщения не считается, одинаковая система при разном user — тоже нет.
В боевых вызовах (разные темы, заголовки фото, картинки) это не случается никогда → 0 % на gemini-3-flash в выгрузке.
Перестановка «статичное первым» сама по себе экономии НЕ даёт.

Явный кэш (`cache_control: {type: "ephemeral"}` на системном сообщении, система одинакова для ниши, всё про статью — первый
текст user; это и есть новая боевая раскладка rate):
| Модель | без кэша, $/вызов | с кэшем (2-й+ вызов) | cached_tokens | экономия вызова |
|---|---|---|---|---|
| gemini-3-flash-preview (rate) | 0.003340 | 0.002580 | 1711 из 4383 (39 %) | −23 % |
| gemini-2.5-flash-lite | 0.000428 | 0.000279 | 1711 из 2721 (63 %) | −35 % |

Срабатывает со второго вызова всегда (`cache_write_tokens` на первом; запись не дороже обычного вызова), TTL ≈5 мин.
Кэш считается по точному тексту системы: для hair их три (стрижка / цвет / причёска — `specializeProfile` меняет
subject_label и поля фактов), для других ниш — по одному. Между пачками одной статьи и между статьями одной ниши в
пределах ~5 мин — попадание.
Промты модерации (статичная часть 530–720 токенов) и rank (~300) короче минимума (~1024): провайдер их просто не кэширует,
ошибки нет (проверено на lite и gemini-3-flash) — `cacheSystem` у них включён на будущее, экономии сейчас 0.

### Что изменилось
- `src/lib/articles/ai.ts`: `ChatRequest.cacheSystem` — системное сообщение уходит одним текстовым блоком с
  `cache_control: ephemeral`; только для OpenRouter и моделей gemini/claude (`cacheableSystem`: провайдер правила +
  модель рецепта или правила), остальным провайдерам поле не шлём. Шапка файла — результат замера.
- `src/lib/articles/photo/vision.ts`: `VisionRequest.cacheSystem` → `aiChat` (один проброс; файл не в списке владения —
  правка минимальная).
- `worker/articles/stages/rate.ts`: промт собирает чистая `buildRateSystem(inp, rescue)` → `{system, lead}`:
  `system` = текст промта набора (если в его системном тексте нет переменных статьи) + JSON-контракт + HARD REJECT —
  одинаков для всех статей ниши; `lead` = TREND (бриф или общий критерий), TOPIC RULES (контракт, аудитория, мода/интерьер,
  чек-лист), «when in doubt, reject», SECOND PASS — первый текст user, затем прежний текст пачки и фото. Поправки
  CORRECTION_FLAT / CORRECTION_AUDIENCE дописываются к `lead`, а не к системе. Встроенный `ratingSystemFor` уже содержал
  HARD REJECT, а TOPIC RULES повторяли его второй раз — дубль убран. Схема JSON и формулировки правил не менялись.
  Системный текст набора с переменными (`{{topic}}` и т.п.) считается зависящим от статьи и уходит в `lead`.
  `HARD_REJECT_RULES`, `buildRateSystem`, `RateSystemInput` экспортированы (стенд).
- `src/lib/articles/aiModeration.ts`: `sysTopic / sysOpinion / sysDispute / sysDetail` возвращают `{system, lead}`;
  система без ключа (персона, общие правила `COMMON_STATIC`, список причин, JSON), `lead` = `ARTICLE KEYWORD`, правила темы
  (`focusRules` + `keywordVisualRule`), тренд и норма фото; `callModel` ставит `lead` первым текстом user и шлёт `cacheSystem`.
  У `sysDetail` ключ уже есть в первой строке блока крупных кадров — из системы убран. `MODERATION_PROMPTS` экспорт для стенда.
- `worker/articles/stages/rank.ts`: тема — первой строкой user, `cacheSystem`.
- `src/lib/articles/photo/ranking.ts`, `select.ts` — без изменений.

Ожидание по кэшу: rate — 1.7k статичных токенов × ~15.8 вызовов по 0.25 цены ≈ −$0.002…0.003 на статью (gemini-3-flash
~$0.5–0.75/M за текстовый ввод) — в пределах оценки волны 3 (−$0.003…0.005); модерация и rank — 0 до тех пор, пока их
статичная часть короче минимума. Учёт cached_tokens в `UsageLog` не делал: нужна колонка в схеме (и цена OpenRouter уже
приходит точной в `usage.cost`, экономия видна по `costUsd` как есть).
