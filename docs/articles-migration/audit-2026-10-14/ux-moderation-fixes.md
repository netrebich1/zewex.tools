# Модерация фото: исправления по аудиту удобства (2026-10-15)

Аудит: `ux-moderation.md` (в этой папке). Сделаны пункты P0 1–3 и P1 4–6. Не задеплоено: проверено в копии `/root/zewex-check` (tsc веб + воркер, `next build`) и скриптом только на чтение по боевой базе.

## P0-1. Решение ИИ видно прямо в модерации фото
- `photoState` отдаёт `ai` (`ModAiContext`), то есть последнее решение ИИ по статье, кроме заменённых перепроверкой. Показывается только для PHOTO_REVIEW.
- В шапке появилась жёлтая плашка, например «Проверено ИИ: отдано людям — много фото не по теме (8 из 18); впритык к минимуму». Если ИИ был за одобрение, но не уверен, это написано отдельно. Ниже: уверенность, сколько убрано и добавлено, норма, сколько фото сейчас (если фото больше нормы, это выделено), мнение модели. Для тест-режима плашка называется «Предложение ИИ (тест), правки не применены».
- Метки в сетке:
  - «ИИ ✕» вместо «снято» и причина под кадром, по-русски: «коллаж или скриншот», «не по теме: …». Причина берётся из `removed[]` решения, для старых решений из события `exclude` ИИ.
  - «+ИИ» и причина у кадров, которые ИИ добавил из резерва.
  - В тест-режиме: «ИИ: убрать?» на кадрах статьи и «ИИ: добавить?» в резерве.
  - Если фото больше плана, на панели появляется метка «больше плана (N) на M».
- Кнопка «Отменить правки ИИ» (`undoAiEdits` в `moderation.ts`, действие `undo_ai` в API). Возвращает снятые ИИ кадры, убирает добавленные ИИ, восстанавливает порядок до проверки. Кадры, которые человек добавил сам, остаются в конце. Работает только для PHOTO_REVIEW и только если статью не держит идущий запуск ИИ или коллега. Проверка доступа идёт через `canAccessArticle`. Внутри используются `restorePhoto`, `removePhoto` и `reorderPhotos`, в журнал пишется событие `ai_undo`.

## P0-2. Статьи больше не теряются у ИИ
- `releaseRunHolds(runId)` в `aiModeration.ts`. Когда запуск завершается (`finishRunIfIdle`) или его останавливают (`stopAiRun`), захват `aiRunId` снимается со всех его статей. Раньше снимался только с непроверенных. Не трогаются только статьи, которые прямо сейчас в обработке (processing/applying моложе 6 минут). Предложения тест-режима и при `autoApply=false` остаются на экране «ИИ-модерация», но сами статьи сразу попадают людям в группу «От ИИ».
- Самолечение `releaseFinishedHolds()` запускается на каждом проходе автозапуска (раз в 20 с, в воркере). Оно отпускает статьи, которые держат запуски в статусе done/stopped/failed или уже удалённые запуски.
- Выдача людям: `nextForReview`, `claimArticle`, `waitingCounts` учитывают захват только от идущего запуска (`liveAiRunIds` / `notHeldByAi`). Пустой захват завершённого запуска `claimArticle` снимает сам.
- `resolveResult` («Применить» на экране ИИ-модерации) отказывает, если статью сейчас правит другой сотрудник.
- Счётчики:
  - `moderationCounts` возвращает `{ photos, insufficient, articles }`. `photos` считает PHOTO_REVIEW без статей на проверке у идущего запуска ИИ.
  - «Мало фото» (INSUFFICIENT_PHOTOS и WAITING_FOR_PHOTOS) считается отдельно. На Обзоре для него отдельная кнопка «Мало фото (N)».
  - Чипы сайтов и подзаголовок страницы считают так же, как список.

## P0-3. Очередь списком
- `/pinterest/articles/moderation/photos` без параметров теперь показывает список и **ничего не закрепляет**. Компонент `PhotoQueueList.tsx`, данные `photoQueue()`.
  - Вкладки: «От ИИ» (ИИ отдал людям или предложил правки в тесте, с причиной и уверенностью), «Новые» (ИИ не смотрел), «Мало фото».
  - Фильтр по сайту (чипы), поиск по ключу или сайту.
  - В строке: сайт, сколько ждёт, фото и план (красным, если меньше нужного; оранжевым, если больше плана), кто держит (🔒).
  - Вкладка запоминается в адресе (`?group=`).
- По клику статья открывается в прежнем режиме проверки по одной (`?article=<id>`), закрепление ставится при открытии. Кнопка «Начать проверку» (`?work=1`) запускает конвейер «следующая свободная». Из конвейера в список ведёт кнопка «Список».
- «Мало фото» прямо в строке: «На модерацию», «Добрать фото», «Закрыть» (действие `close` в API), «Карточка».
- Статьи, которые сейчас проверяет ИИ, в список не входят. Под вкладками выводится строка «Ещё N сейчас проверяет ИИ».

## P1-4. Закрепление
- Каждое редактирующее действие в API продлевает `claimedAt` (`extendClaim`).
- Пока статья открыта, раз в минуту уходит пинг `heartbeat`, который закрепляет или продлевает статью. Если статью перехватил коллега, показывается предупреждение.
- При уходе со статьи (переход внутри портала, смена статьи, закрытие вкладки через `pagehide`) уходит `release` через `navigator.sendBeacon`. Если вкладку восстановили из bfcache, сразу уходит пинг.
- Ложное «Всё проверено» исправлено. Пустое состояние теперь объясняет причину: «Вы пропустили N», «Сейчас проверяет ИИ: N», «Открыты у коллег: N» (`queueBlockers`, приходит в ответе `next`). Есть кнопки «Вернуться к пропущенным (N)», «Проверить ещё раз», «К списку».

## P1-5. Одобрение, отмена, телефон, меню
- Enter и «Одобрить и писать» сначала просят подтверждения («Проверьте перед одобрением: ИИ добавил 7 кадров из резерва, в статье 22 фото при плане 15»), если ИИ добавил кадры или фото больше плана. Второй Enter или «Да, одобрить» подтверждает.
- «Добавить из резерва» теперь можно отменить (Ctrl+Z или «↶ Отменить»): только что добавленный кадр убирается (`remove`).
- На сенсорных экранах кнопки ✕, «Устарело» и «Вернуть» видны всегда (`@media (hover:hover)` прячет их только там, где есть мышь). Для смены порядка есть стрелки ◀ ▶, так как перетаскивание на телефоне не работает. С клавиатуры кнопки открываются по фокусу.
- В меню сервиса (`ArticlesNav`) появились счётчики «Модерация фото · N» и «Модерация статей · N», по тем же правилам, что Обзор и список. Первое значение приходит из `layout.tsx`, потом меню обновляет его при переходах и раз в минуту (`GET /api/articles/moderation?counts=1`).

## P1-6. Названия вкладок резерва
- «Одобрены ИИ / Отклонены ИИ» переименованы в **«Подходящие по оценке» / «Отклонённые оценкой»**. Это оценка кадров на этапе поиска, а не ИИ-модерация.

## Видимость сотрудников
Все выборки идут через `articleWhere` / `canAccessArticle`. Скрипт только на чтение по боевой базе для каждого активного пользователя показал, что очередь, счётчики Обзора и меню, чипы сайтов и пустое состояние совпадают. У админов: «От ИИ 5 / Новые 3 / Мало фото 0», всего 8. У сотрудников без доступа к сайту: 0 везде.
