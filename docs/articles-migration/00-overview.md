# Pinterest Articles → zewex.tools: сводка переноса

Дата: 2026-10-10. Источник: архивы `zewex-migration.zip` (пакет переноса) и `zewexart-main.zip` (сырой репозиторий Lovable).
Код в обоих архивах идентичен (отличается только `supabase/config.toml` и наличие `drizzle/`, `roadmap.md`, `.lovable/plan`).

Подробные отчёты по зонам — файлы `01…07` в этой папке. Экспорт промтов и конфигов — `prompts.export.json`, `config.export.json`.

## Что это за сервис (одной строкой)

Ключевое слово → поиск реальных вертикальных фото (DataForSEO/SerpApi) → тех. фильтр → ИИ-оценка → отбор ≥15 кадров → модерация фото (человек или ИИ) → план статьи по фото → план секций → секции (одна на фото) → вступление/заключение → SEO-мета → HTML → публикация в WordPress. Второй формат — ИИ генерирует картинки (gpt-image), он вторичен.

Объём исходника: 49 edge-функций (~45 000 строк, из них `_shared` 7 300), 47 таблиц, 68 промтов в 12 наборах, 30 страниц React (~11 000 строк), 7 000 строк клиентской логики.

## Сопоставление слоёв

| Было (Lovable/Supabase) | Будет (zewex.tools) |
|---|---|
| Postgres + RLS по владельцу команды | MariaDB + Prisma; видимость через `src/lib/sites/access.ts` (SiteAccess → команды → сотрудники), как у Пинов |
| Supabase Auth, `team_members`, `canAccessPage` | Пользователи и команды портала (`User`, `Team`, `TeamMember`), роли ADMIN / лидер / участник |

| `generations_log`, `article_cost_report`, `provider_billing_status` | `UsageLog` (refId = id статьи/прогона) + автоотключение ключа при 402/401 (`disableKey`) |

| Supabase Storage (бакеты, render API `/storage/v1/render/image`) | Файловое хранилище `storage/…` → nginx `/files/…`; трансформации через `sharp` локально |
| `sites` (URL, application password, auto_*) | `SiteAccess` (доступ REST API) + сайт сервиса статей (настройки ниши/сценария/автозапуска) |
| `sheets-sync` (Google Sheets) | Вторая волна: импорт ключей из таблицы / файла |
| `telegram-notify` | Вторая волна |
| Lovable AI Gateway (последний фолбэк) | Нет. Цепочка: правило слота портала (OpenRouter → laozhang → OpenAI по `preferProviders`) |
| `pipeline_errors` через триггеры БД | Явная запись ошибки этапа в коде (`finishJob`/`failItem` аналог), страница ошибок |

## Принципы переноса

1. **Логика и промты — как есть.** Все пороги, веса, словари, контракты тем, гигиена текста переносятся 1:1 и фиксируются в отчётах с номерами строк исходника.
2. **Костыли под Supabase — выбрасываем.** Всё, что боролось с лимитом 150 с (sleep-then-chain, самовызовы, 504-как-успех, «бюджет воркера 100 с», разрезание публикации на возобновляемые куски) заменяется обычным длинным этапом с heartbeat и идемпотентностью.
3. **Ключи и расход — через портал.** Никаких ключей в таблицах сервиса; слоты проекта `articles`: текст основная / текст быстрая / vision / картинки / DataForSEO / SerpAPI / Perplexity.
4. **Три уровня настроек, как у Пинов:** система (`/sites`: доступ, команды, видимость) → сайт в сервисе (ниша, сценарий по умолчанию, автозапуск, лимиты, ИИ-модерация) → запуск (ключи, количество фото, режим, публикация черновиком).
5. **Один процесс воркера.** Очередь статей живёт рядом с очередью пинов и подборов доменов в `worker/index.ts`.

## Волны

- **Волна 1 (ядро):** модель данных, seed промтов/ниш/профилей/сценариев, слоты, цепочка real_photo целиком (поиск → публикация), модерация фото человеком, очередь сайта, автозапуск, ошибки, расход.
- **Волна 2:** ИИ-модерация (mix3), эталоны, статистика сотрудников, Telegram, импорт из Google Sheets, бенчмарк/калькулятор.
- **Волна 3:** формат generated_photo (stage 2 → 5 → 6), визуальные промты, референсы.
