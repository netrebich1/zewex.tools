# zewex.tools — провайдеры, ключи, модели (план v2, 2026-10-08)

## 1. Провайдеры

| Провайдер | Тип | Авторизация | Есть модели? | Как получить список моделей |
|---|---|---|---|---|
| OpenAI | LLM, напрямую | Bearer-ключ | да | GET /v1/models + ручное добавление |
| OpenRouter | LLM-агрегатор (OpenAI-совместимый) | Bearer-ключ | да, сотни | GET /api/v1/models (с ценами) |
| laozhang.ai | LLM-реселлер (OpenAI-совместимый, свой base URL) | Bearer-ключ | да | GET /v1/models + ручное добавление |
| Perplexity | LLM с поиском | Bearer-ключ | да (sonar-семейство) | ручной список |
| DataForSEO | Данные SEO | Basic auth (login + password) | нет, вместо моделей — эндпоинты | не нужен |
| SerpAPI | SERP-данные | ключ в параметре запроса | нет, вместо моделей — «движки» (google, bing…) | не нужен |

Выводы для схемы:
- У провайдера настраиваются: `base_url`, `auth_type` (bearer / basic / query), `kind` (llm / data).
- OpenAI, OpenRouter и laozhang ходят через ОДИН адаптер «OpenAI-совместимый API» с разным base_url. Новый реселлер = одна запись в таблице, а не новый код.
- Для DataForSEO и SerpAPI — свои адаптеры, у них нет «моделей».

## 2. Модели

- Таблица `models`: провайдер, model_id (как в API), человекочитаемое имя, возможности (chat / vision / image-gen / search), цена вход/выход (если известна), статус (активна / скрыта / устарела).
- Пополнение: кнопка «Обновить список» тянет GET /models у провайдера и показывает новые модели; админ включает нужные. Плюс ручное добавление для провайдеров без такого эндпоинта.
- Одна и та же модель (например gpt-4o) существует у OpenAI, OpenRouter и laozhang как три разные записи. Это намеренно: у них разный ключ, цена и путь.

## 3. Слоты проекта (главная идея)

Проект (инструмент) не называет провайдера и ключ в коде. Он объявляет **слоты** — что ему нужно:

```
Проект «Генератор описаний пинов»
  слот text_main   — «Основная генерация текста» (LLM, chat)
  слот text_cheap  — «Черновые варианты»          (LLM, chat)
  слот serp        — «Выдача Google»              (data, serp)
```

Для каждого слота задаётся **привязка** = провайдер + модель (если LLM) + ключ. Привязки задаются на уровнях:

| Приоритет | Уровень | Смысл |
|---|---|---|
| 1 | пользователь + проект | личная настройка одного человека для одного инструмента |
| 2 | команда + проект | команда «Gambling» в этом инструменте ходит через ключ Б, модель X |
| 3 | проект | значение по умолчанию для инструмента |
| 4 | команда | для всех инструментов команды (по типу слота) |
| 5 | глобально | запасной вариант портала |

При запросе берётся самая частная привязка. Это и даёт: «один сервис, я и партнёр, у каждого свой ключ».

## 4. Ключи: один ключ — много проектов и команд

- Таблица `api_keys`: провайдер, ярлык («OpenRouter — мой»), секрет (зашифрован), хвост для показа, владелец, статус, лимит (опционально).
- Ключ НЕ принадлежит проекту или команде. Он просто существует, а **привязки** (п.3) ссылаются на него. Один ключ может стоять в десяти привязках: три проекта, две команды — без копирования.
- На странице ключа показывается список «где используется», с переходом в каждую привязку.
- Удаление ключа запрещено, пока на него есть привязки (сначала показать, куда он подключён).

## 5. Поток запроса (бэкенд-прокси)

1. Инструмент вызывает внутренний API: `POST /ai/run { slot: "text_main", input… }` с сессией пользователя.
2. Сервер по пользователю → команда(ы) → проект → слот находит привязку (приоритеты п.3).
3. Берёт ключ, расшифровывает, выполняет вызов через адаптер провайдера.
4. Пишет строку в `usage_log`: кто, проект, слот, провайдер, модель, ключ, токены / единицы, стоимость, длительность, ошибка.
5. Ключи никогда не попадают в браузер.

## 6. Интерфейс управления

- **Ключи** — список по провайдерам, «где используется», проверка ключа кнопкой «Проверить» (тестовый запрос).
- **Модели** — по провайдерам, кнопка «Обновить список», включение/выключение.
- **Проекты** — карточка проекта: слоты и их привязки по умолчанию.
- **Команды** — участники + переопределения привязок по проектам.
- **Проверка маршрута** — выбрать пользователя + проект + слот → показать, какой ключ и модель применятся и какое правило сработало.
- **Расход** — по ключам / командам / проектам / людям за период.

## 7. Открытые вопросы (нужны ответы)

1. Perplexity «для реселлеров» — это свой ключ Perplexity, или Perplexity-модели через laozhang / OpenRouter? Если второе — отдельный провайдер не нужен.
2. laozhang — используем как полный OpenAI-совместимый шлюз (GPT, Claude, Gemini через него)? Какие модели там нужны в первую очередь?
3. Нужны ли лимиты: месячный бюджет на ключ / команду / человека с блокировкой или только с предупреждением?
4. Автоматический запасной вариант: если провайдер упал или ключ исчерпан — переключаться на вторую привязку слота или просто возвращать ошибку?
5. Могут ли обычные участники добавлять личные ключи (уровень 1), или ключи заводит только админ?
6. Кто видит расход: только админ, или каждый видит свой, а лидер команды — команду?
7. Роли: достаточно «админ / участник», или нужен «лидер команды» (управляет привязками только своей команды)?
8. База: на сервере стоит MariaDB от FASTPANEL. Используем её или ставим PostgreSQL (я бы предпочёл PostgreSQL)?
