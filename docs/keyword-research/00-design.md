# Подбор ключей Pinterest — архитектура и план

Статус: **согласовано владельцем 2026-10-20** (ответы — в конце документа).
Инструмент: раздел Pinterest → «Подбор ключей», адрес `/pinterest/keywords`, slug `keywords`.

## Коротко для владельца

Всё, что сейчас собирается вручную через Claude в Chrome и живёт в Google Таблице (вкладки Evergreen, Новые ключи, Конкуренты), переезжает в zewex.tools:

1. **Портал** хранит ключи, частотность и снимки выдачи, сам считает оценку 0–100, вердикт и флаги, показывает таблицу с фильтрами, сортировкой, процентами рядом с каждым количеством и графиками. Работает с любого компьютера, и с Mac тоже.
2. **Расширение Chrome «Zewex Collector»** ставится в браузер, где открыт Pinterest (Mac или Windows). Оно берёт у портала список ключей, по очереди спрашивает выдачу у Pinterest так же, как это делал прототип, и отправляет результат в портал. Само сбавляет темп и делает паузы, если Pinterest начинает отказывать. Аккаунтов может быть несколько: расширение в каждом браузере работает со своим аккаунтом, портал раздаёт задания по очереди.
3. **Частотность** (аудитория Ads Manager US/мес) собирает то же расширение на странице Ads Manager. Официальный Pinterest API не используем (решение владельца).
4. **Дальше**: отобранные ключи одной кнопкой уходят в запуск статей и в пины (вариации, заголовки).

Выдача Pinterest у каждого аккаунта своя, поэтому у каждого снимка выдачи записано, с какого аккаунта он снят (SEO Netrebich, W…).

## Почему сбор в браузере, а не на сервере

Pinterest отдаёт выдачу только залогиненному браузеру с живыми cookie и csrf-токеном. Если запрашивать с сервера, он заблокирует запросы почти сразу, а заходить на сервере под аккаунтом опасно для аккаунта. Поэтому правило такое: **сбор идёт там, где есть сессия Pinterest**, то есть в браузере владельца или сотрудника. Сервер только раздаёт задания, принимает ответы и всё считает. Даты статей конкурентов — обычные сайты, их сервер забирает сам.

```
 Браузер с Pinterest (Mac/Win)                  zewex.tools (сервер)
 ┌───────────────────────────┐   задания       ┌─────────────────────────────────────┐
 │ Zewex Collector (MV3)     │ ◀────────────── │ API /api/keywords/collector/*        │
 │  • BaseSearchResource     │                 │ очередь KwTask, аккаунты KwAccount   │
 │  • AdvancedTypeahead      │ ──────────────▶ │ разбор ответа → KwSerpSnapshot/KwPin │
 │  • UserResource (авторы)  │  сырые ответы   │ метрики, оценка, вердикт, флаги      │
 │  • Ads Manager: sizing    │                 │ воркер: даты статей, пересчёт        │
 └───────────────────────────┘                 │ UI: Ключи / Новые / Конкуренты / …   │
                                               └─────────────────────────────────────┘
```

## Что переносится из прототипа (не придумываем заново)

Прототип: браузерные скрипты в истории сессии 18fe03bc + Python в её папке. Логика переносится один в один:

| Прототип | В портале |
|---|---|
| `__analyze` (JS): первые 20 пинов, реклама `is_promoted`, товары (`rich_summary.type_name=product`, `product_pin_data`, `shopping_flags`), инфо/без ссылки, видео, свежесть <90/<180 дней, ключ в заголовке, число в заголовке, медиана сохранений и подписчиков, домены топ-10, «крупные СМИ» (`__BIG`), владелец сайта или пересохранение (`__ownGuess` + подтверждённый домен), профили авторов топ-10 (`ul`: просмотры, охват, подписчики, пины, доски, бизнес, подтверждённый сайт, магазин) | `src/lib/keywords/serp.ts`: разбор сырого ответа на сервере, результат того же формата `SerpAgg` |
| `build_tail.py`: `verdict`, `score`, `flags`, `variants`, `prof`, `art_stats`, `year_flag` | `src/lib/keywords/metrics.ts` |
| `competitors.py` | `src/lib/keywords/competitors.ts` + вкладка «Конкуренты» |
| `artdates.py` (метатеги `article:published_time`, `datePublished`, `<time>`, дата в адресе) | воркер `worker/keywords.ts` |
| `classify.py` (сезонность: жёсткая отсекается, мягкая и «тренд» помечаются) | `src/lib/keywords/season.ts` |
| `gen.py`, `queue.py` (кандидаты, очередь частотности) | генератор кандидатов (этап 3) |
| Паузы `__backoff=[2,4,8,15]` мин, пауза между ключами 5–8 с | расширение + состояние аккаунта |
| Ads Manager: перехват XHR `get_audience_sizing_handler`, ключ в кавычках и в нижнем регистре, сверка с кэшем | расширение, режим «частотность» |

## Данные (Prisma, MariaDB)

Все модели с префиксом `Kw`. Данные исследования общие для всех, кому открыт инструмент: это база ключей, а не личные заметки.

- **KwAccount**: аккаунт Pinterest, с которого снимается выдача. Поля: `name` («SEO Netrebich», «W»), `username`, `status` (ACTIVE / SLOW / LIMITED / OFF), `limitedUntil`, `gapSec` (пауза между ключами), `dailyCap` (по умолчанию пусто = без лимита), счётчики за день, `lastSeenAt`.
- **KwAccountEvent**: журнал аккаунта — каждый запрос (время, тип, успех/пустая выдача/ошибка) и каждая блокировка с её длительностью. Из него видно, после скольких запросов и с каким темпом Pinterest ограничивает поиск и через сколько снимает ограничение.
- **KwCollector**: установленное расширение. Хранит хэш токена, пользователя портала, аккаунт и `lastSeenAt`. Токен выдаётся на вкладке «Сбор».
- **KwKeyword**: ключ. `phrase` (как в таблице), `norm` (нижний регистр, уникален), `niche` (nails / outfits / hair), `source` (sheet / autocomplete / generated / manual), `season` (none / soft / trend / hard), `status` (new / picked / rejected / sent), поля таблицы статей (`seoKeyword`, `focusKeyword`, `scenario`, `mode`), `clusterId`. **Последние посчитанные метрики хранятся прямо в строке** (`volume`, `score`, `verdict`, проценты рекламы, товаров, свежих пинов и бизнес-аккаунтов, медиана сохранений, ключ в заголовке, средняя дата статей и т. д.), чтобы фильтры и сортировка работали запросом к базе. Полный набор — в `metrics` (JSON).
- **KwVolume**: история частотности: `estimate`, `lower`, `upper`, `none` (нет данных), `source` (ads_ui), `region` (US), `takenAt`.
- **KwSerpSnapshot**: один снимок выдачи. `keywordId`, `accountId`, `takenAt`, `agg` (JSON формата прототипа: n, org, ad, prod, …, ul), подсказки `typeahead`, уточнения `guides`. Снимки копятся: видно, как выдача меняется со временем.
- **KwPin**: пины топа снимка: позиция, id пина, ссылка, домен, дата пина, сохранения, реклама/товар/видео, заголовок, автор.
- **KwPinner**: кэш профилей авторов (UserResource): просмотры, охват, подписчики, пины, доски, бизнес, подтверждённый домен, магазин; срок жизни 30 дней, расширение не спрашивает лишний раз.
- **KwArticle**: дата публикации статьи по ссылке (`url`, sha1, `publishedAt`, `fetchedAt`, `status`).
- **KwDomain**: сайт-конкурент: тип (платформа/магазин или сайт/блог), посчитанная сводка для вкладки «Конкуренты».
- **KwCluster**: группа ключей одной темы (ниша, главный ключ). Нужна, чтобы не писать две статьи под один интент.
- **KwTask**: очередь для расширения: `kind` (serp / volume / typeahead / pinner), `keywordId`, `accountId` (если важно, с какого аккаунта), `status`, `attempts`, `leaseUntil`, `error`.

## Расчёт метрик

- Вердикт (✅ изи / 🟡 средний / 🔴 тяжёлый / ❌ реклама/товары / ❌ мало частоты), оценка возможности 0–100, флаги (📹 🏢 🎯 👶 🕰 🔁 🔒), вариации ключа и «ищут с годом» считает `metrics.ts` по последнему снимку и последней частотности. Формулы как в `build_tail.py`.
- Пересчёт идёт при приходе нового снимка или частотности и раз в сутки (возраст статей растёт сам).
- Порог частотности по умолчанию 3000, меняется в фильтре.
- Сверка переноса (2026-10-20): на стартовых данных оценка, вердикт, флаги и вариации совпали с прототипом во всех 1536 строках. Отличие одно: «ищут с годом». В прототипе регулярка испорчена (вместо `\b` — символ backspace), поэтому в Таблице колонка всегда пустая. В портале работает задуманная логика `\b202[5-9]\b`.

- **Доработки 2026-10-20 (по разбору данных, решение владельца):**
  - *Позиции.* Свежесть пинов топ-10 считается с весом места `1/log2(место+1)`: 1-е место весит 1.0, 3-е 0.5, 10-е 0.29. В оценке это слагаемое заменило «свежих из 20» с весом 0.2 вместо 0.25: на стартовых данных средний вклад тот же (0.28 × 0.2 ≈ 0.22 × 0.25), сдвиг оценок в среднем +0.9, по модулю 2.2. Вердикт не менялся. Добавлены флаг «🆕 свежий пин в топ-3» и колонки: свежие с весом места, свежих на местах 1–3, со ссылкой на местах 1–5, сохранения мест 1–3.
  - *Статьи конкурентов.* Воркер вместе с датой берёт заголовок (og:title → h1 → title), год в нём, а также число слов, фото и H2 в основной части страницы. Старые строки `KwArticle` (`detailsAt = null`) он перечитывает по 100 за проход. Год устаревший, если он меньше текущего; ищется в заголовке статьи, затем в заголовке пина, затем в адресе. Флаг «📅 устаревшие годы» ставится от 2 таких статей в топ-10; в оценке бонус `доля × 0.15` от статей со ссылкой. В пробе на 100 статьях 2026 года почти все заголовки с годом были 2026, так что флаг срабатывает редко.
  - *Сравнение аккаунтов* (вкладка «Сравнение аккаунтов», `KwCompare`, `lib/keywords/compare.ts`). Выборка из 25 ключей с частотностью от 3000, поровну по нишам, ставится в очередь выдачи на оба аккаунта. Сравниваются только снимки после создания выборки: совпадение пинов топ-10 и топ-3, сдвиг позиций, вердикт, оценка. Вывод: «можно доверять», если вердикт совпадает в ≥ 85% ключей и оценка расходится в среднем ≤ 8; «для отбора можно, пограничные — с двух аккаунтов», если ≥ 65% и ≤ 15; иначе «выдача сильно зависит от аккаунта».

## Экран

`/pinterest/keywords`, вкладки:

- **Ключи**: все ключи из таблицы и подтверждённые новые. Сверху карточки (всего, с частотностью, со снятой выдачей, сколько ✅/🟡/🔴/❌) и график распределения по вердиктам и частотности. Фильтры: поиск, ниша, вердикт, частотность от/до (по умолчанию от 3000), реклама % до, товары % до, свежих пинов от, медиана сохранений до, бизнес-аккаунты % до, ключ в заголовке % до, средний возраст статей от N месяцев, сезонность, аккаунт снимка, флаги. Сортировка по любой колонке. Рядом с каждым количеством стоит процент (5 · 25%). По клику строка раскрывается: топ-10 со ссылками и датами, вариации, подсказки поиска, уточнения, история снимков.
- **Новые**: кандидаты не из таблицы (подсказки поиска, генерация) с той же таблицей. Из этой вкладки ключи можно взять в работу, отклонить или поставить в очередь сбора.
- **Конкуренты**: сайты, которые держат топ-10 по многим ключам (как `competitors.py`).
- **Кластеры**: группы ключей одного интента.
- **Сбор**: аккаунты и их состояние (работает / медленно / ограничен до …), расширения, очередь, кнопки «пауза» и «снять выдачу заново», загрузка стартовых данных.

Выгрузка: CSV/TSV отфильтрованного списка. Есть формат «для запуска статей» с колонками Keyword / SEO Keyword / Focus Keyword / Сценарий / Режим, как в Google Таблице.

## Расширение «Zewex Collector»

- Chrome MV3, ставится «Загрузить распакованное» из папки `extension/collector` (на Mac и на Windows одинаково). Позже можно выложить в Chrome Web Store как закрытое.
- В окне расширения вставляется токен с вкладки «Сбор». Аккаунт Pinterest расширение узнаёт само по сессии (имя пользователя) и сообщает порталу.
- Content script на `www.pinterest.com` делает те же запросы, что прототип (`BaseSearchResource`, `AdvancedTypeaheadResource`, `UserResource` с `x-csrftoken` и `x-pinterest-pws-handler`) и отдаёт **сырые** JSON в портал. Разбирает их сервер, поэтому исправить разбор можно без переустановки расширения.
- Темп задаёт портал (`gapSec` аккаунта, суточного лимита по умолчанию нет). На пустую выдачу или ошибку («search is overwhelmed») расширение делает паузы 2 → 4 → 8 → 15 мин. После 15 мин портал помечает аккаунт LIMITED на несколько часов и отдаёт задания другому аккаунту.
- Аккаунт SEO Netrebich получил ограничение после ~170 быстрых запросов, но сколько длится блок и какой темп безопасен, пока неизвестно. Поэтому суточного лимита по умолчанию нет (решение владельца): пауза 8–15 с со случайным разбросом, ступенчатые паузы при отказах и журнал `KwAccountEvent`. На вкладке «Сбор» видно, сколько запросов прошло до блока и сколько он длился. Лимит можно включить у аккаунта, когда наберётся статистика. Для W — медленный режим (пауза больше).
- Режим «частотность»: на открытой странице черновой кампании Ads Manager расширение вписывает ключ в поле ключевых слов и перехватывает ответ `get_audience_sizing_handler`.

## Частотность

- Только Ads Manager через расширение (официальный API v5 `audience_sizing` / Trends не используем — решение владельца 2026-10-20). Нужна открытая вкладка черновой кампании рекламного аккаунта 549767483773; расширение вписывает `"ключ"` в поле ключевых слов и берёт `reach_estimate` из перехваченного `get_audience_sizing_handler` (точное значение, даже когда экран пишет «< 10k»). Прямой повтор запроса даёт 403, поэтому только через поле.
- Частотность меняется медленно: пересъём не чаще раза в 60 дней.

## Выход в другие сервисы

Прямую кнопку «запустить статьи» делаем вместе с чатом статей: их файлы (`src/lib/articles/*`, `worker/articles/*`, `pinterest/articles/*`) этот инструмент не трогает. Нужна точка входа «запуск из списка ключей», такая же, как импорт из таблицы.

## Этапы

1. **База и список** (этот заход): модели `Kw*`, библиотека метрик (перенос `build_tail.py`), загрузка стартовых данных (`evergreen.tsv`, `vol.json`, `serp.json` + `serp_w.json`, `artdates.json` лежат в `prisma/seed-data/keywords/`, кнопка «Загрузить стартовые данные» на вкладке «Сбор»), вкладки «Ключи» и «Новые» с фильтрами, сортировкой, процентами, карточками, графиком и раскрытием строки, выгрузка CSV.
2. **Сбор**: API сборщика, очередь, аккаунты, расширение, разбор сырых ответов на сервере (перенос `__analyze`), кэш авторов, даты статей в воркере, вкладка «Конкуренты». **Написан 2026-10-20** (вместе с режимом Ads Manager в расширении), не задеплоен; установка расширения — `extension-install.md`.
3. **Частотность и кандидаты**: режим Ads Manager в расширении, генерация кандидатов (`gen.py`), расширение по подсказкам, сезонность.
4. **Кластеры и выход**: кластеры, история снимков на графиках, передача в статьи и пины.

## Решения владельца (2026-10-20)

1. Схема «сервер + расширение Chrome» — да.
2. Суточный лимит на аккаунт — без лимита: о времени блока пока ничего не известно. Копим статистику в журнале аккаунта, лимит включаем позже по данным.
3. Доступ — по галочке, как остальные инструменты (админы видят всегда).
4. Официальный Pinterest API — нет, частотность только через Ads Manager.
