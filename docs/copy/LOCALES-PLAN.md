# Мешап-статьи на других языках (чешский, немецкий, польский, румынский) — план

Запрос владельца 17.11.2026: собирать статьи из нашего же банка кадров для сайтов на других языках, под Google Discover.
Главное — не переводить ключи дословно, а подбирать то, как ищут в Чехии/Германии/Польше/Румынии. Лимиты кадров
английского мешапа на другие языки не распространяются: кадр, использованный 3 раза по-английски, может ещё 3–5 раз
уйти в чешские статьи. Промпты потом пересмотрим целиком.

## 1. Где живёт: отдельный модуль в Discovery, общий только банк кадров

Новый раздел `/discovery/locale` («Статьи на языках»), код `src/lib/locale/*`, свои таблицы с префиксом `Loc*`.
От «Article Copy» берётся только чтение банка: `ArtPhoto` (sha256, phash, facts, description, wpUrl) и `CopyCore`
(ядра и кластеры слов). Ничего в таблицах Copy* не меняется, счётчики не пересекаются.

| Таблица | Что хранит |
|---|---|
| `LocLanguage` | язык + страна (cs-CZ, de-DE, pl-PL, ro-RO), коды DataForSEO (location_code 2056 / 2276 / 2616 / 2642, language cs / de / pl / ro), модель-полировщик, год |
| `LocSite` | сайт WordPress (переиспользует `SiteAccess`), язык, ниши, лимиты кадра на сайт, карта категорий |
| `LocKeyword` | ядро → язык → подобранный ключ: focus (без года), SEO-ключ (с годом), объём, кандидаты с объёмами, лёгкость выдачи, статус auto / approved / rejected, кто и когда |
| `LocArticle` | связь статьи (`Article`) с ядром, языком, сайтом, английской статьёй-источником, стадией (en_draft → translated → polished → published) |
| `LocPhotoUse` | (sha256, язык) → число использований; плюс список статей — для лимитов «на тему», «всего», «на сайт» внутри языка |

Лимиты кадра считаются **внутри языка**: `maxUsesPerCore`, `maxUsesTotal`, `maxPerSite` и `maxOverlapPct` — те же
правила, что в Copy, но по `LocPhotoUse` данного языка. Английские использования в них не входят. Между языками
пересечение разрешено полностью, в том числе один и тот же набор кадров (владелец: «это не проблема»).

## 2. Ключи: как перевести «как ищут», а не «как пишется»

**Сделано 17.11.2026 (этап 1, первый прогон).** Клиент шлюза `src/lib/locale/semrush.ts` (phrase_these / phrase_related,
CSV, повтор при 503, кэш замеров на диске `docs/copy/locale/.semrush-cache.json` на сервере), языки `src/lib/locale/languages.ts`,
скрипт `scripts/locale/keywords.ts` (кандидаты gemini-2.5-flash → замер → related для лучших → проверка смысла моделью →
выбор по объёму × (1 − 0.6·KD/100) → склейка дубликатов → TSV). Чешский, по 10 ВЧ-ядер на нишу, ≈ 3 800 юнитов:
волосы 8 из 10 (účesy 8 100, kudrnaté vlasy 3 600, krátké účesy 2 900, melíry 2 400, blond vlasy 1 300, drdoly 1 000),
ногти 7 из 10 (nehty 18 100, růžové nehty 1 300, francouzské nehty 1 000, nail art 1 000, krátké/černé nehty 720, hnědé 480),
образы 3 из 10 (svatební šaty 9 900, outfit 3 600, casual 1 600) — в Чехии почти не ищут «X outfits»: concert/jeans/boots/party
outfits дают 10–210 в месяц. Таблицы: `docs/copy/locale/cs-{hair,nails,outfits}.tsv` (колонка candidates: `*` — из related,
`~` — модель отклонила по смыслу). Известные промахи проверки смысла: «half up half down» → «účesy polodlouhé vlasy»,
«brown hair» → «světle hnědé vlasy» (сужение) — нужна правка владельцем в словаре. Шлюз Group by SEO утром 17.11 два часа
отдавал 503 на весь SEO API (Trends работал) — клиент повторяет запрос, скрипт можно просто перезапустить.
Расход: ≈ 100 юнитов на ядро без related, ≈ 130 с related у трети ядер; 467 ВЧ-ядер женских ниш ≈ 50–60 тыс. юнитов.


Это сердце задачи. Схема — «кандидаты → замер → выбор → словарь», один раз на ядро и язык, результат служит всем
сайтам этого языка.

**Шаг 1. Кандидаты (модель, ≈ $0.001 на ядро).** Для ядра с его кластером слов (`clusterWords`) и нишей просим
gemini-2.5-flash дать 8–12 вариантов, как носитель набрал бы это в Google: синонимы (cs: «nehty» / «gelové nehty» /
«manikúra»; de: сложные слова «Herbstoutfits», а не «Herbst Outfits»), падежи и число, с диакритикой и без
(чехи и поляки часто ищут без неё — Google склеивает, но автодополнение разное), хвосты «nápady / inspirace / Ideen /
pomysły / idei». Промпт просит именно поисковые формулировки, не перевод.

**Шаг 2. Замер и расширение (Semrush API, решение владельца 17.11).** Владелец подключает Semrush API через
group-buy (Group by SEO). Базы Semrush есть для всех нужных стран: `cz`, `de`, `pl`, `ro`, `es`. Запросы:
- `phrase_these` (Keyword Overview для списка) — объём, KD %, CPC, число результатов по каждому кандидату за один вызов;
- `phrase_related` и `phrase_fullsearch` для 2–3 лучших кандидатов — реальные формулировки рынка, которых мы не придумали;
- `phrase_questions` не нужен: вопросные ключи в нашей нише почти не ищут (данные 20.10 по Pinterest, у Google похоже).
Источник объёмов спрятан за адаптером `src/lib/locale/volume.ts` (`semrush` | `dataforseo`): если лимит group-buy
кончится или данные по cs/ro окажутся пустыми, переключаемся на DataForSEO без правок остального кода. Все замеры
кэшируются в `LocKeywordVolume` (ключ, база, месяц) — одно ядро замеряется один раз на язык.
Pinterest Ads sizing по стране — второй источник, только если сайт пойдёт и в Pinterest; для Discover основа — Google.

**Шаг 3. Выбор.** Балл = объём × лёгкость. Лёгкость первым приближением — KD % из Semrush (дёшево, уже в ответе
`phrase_these`); проверка топ-10 по стране (есть ли блоги, не забито ли видео и маркетплейсами) — только для ВЧ-ключей
и только если владелец захочет, через DataForSEO `serp/google/organic`. Берём лучший по баллу с объёмом ≥ порога языка (для cs/ro порог ниже, чем для de/pl — рынки меньше;
стартовые пороги 300 / 1000 / 500 / 300 для cs / de / pl / ro, настраиваются в `LocLanguage`).

**Шаг 4. Склейка.** Два английских ядра часто сходятся в одну фразу («lob haircut» и «long bob» → «dlouhý bob»):
если выбранный ключ уже занят другим ядром этого языка, второе ядро помечается как дубликат и статей не получает,
а его кадры добавляются в пул первого. Это даёт меньше тем, чем по-английски, но без каннибализации.

**Шаг 5. Словарь и ручная правка.** Экран «Ключи языка»: таблица ядро → ключ → объём → кандидаты, кнопки
«одобрить / заменить / отклонить», массовый импорт/экспорт CSV. Автовыбор помечен `auto`; партия может собирать
только `approved` или и `auto` (настройка). Ключи, которые владелец уже перевёл сам (из таблиц «Темы 2027»),
импортируются с статусом approved и замеряются только для справки.

Стоимость подбора: в юнитах Semrush ≈ 10 юнитов за строку Overview и 40 за строку related; на ядро и язык
≈ 150–300 юнитов (12 кандидатов + 2 запроса related по 10 строк), 1 500 ядер × 4 языка ≈ 1–2 млн юнитов — в рамках
group-buy это копейки; точную цену скажет тариф владельца. Модель на кандидаты ≈ $0.001 на ядро.

## 3. Текст статьи: пишем сразу на языке (решение владельца 17.11)

Вариант «английский черновик → DeepL → полировка» владелец отклонил: перевод портит текст, и лишний этап не нужен.
Статья пишется сразу на целевом языке тем же конвейером мешапа: переменные `language` и `target_country` в сценариях
уже есть, кадры и их факты остаются английскими (планировщик и писатель их понимают), на языке пишутся план секций,
H2, текст, вступление/заключение, H1/мета/alt/подписи. H1/мета/slug строятся от `LocKeyword`, slug без диакритики.
Если позже понадобится та же статья на другом языке — DeepL-модуль Discovery переведёт уже внутри системы, по решению
владельца на каждый случай.

Что это меняет в конвейере:
- **Писатель.** deepseek-v4-flash по-чешски, по-польски и по-румынски заметно слабее, чем по-английски (род, падежи,
  калька с английского). Первая партия — A/B писателя на языке: deepseek против gemini-2.5-flash-lite против
  gemini-2.5-flash, судья с промптом на этом языке и носитель (владелец или его человек) на 3–5 статьях. Механизм A/B
  (`writerModel`/`planModel` партии) уже есть. Ожидаемая цена ≈ $0.02–0.03 за статью: диакритика и флексия дают
  на 20–40 % больше токенов, чем английский.
- **Чистки кодом.** Все детерминированные чистки (штампы, салонные реплики, hair length, sentence case, повторы)
  заточены под английский — на языке они отключаются, а их место занимают правила в промпте писателя и один проход
  против повторов (`copyDedupe`, он языконезависим: ищет повторяющиеся n-граммы, модели даёт список). Словари
  штампов на языках заводим по итогам первых аудитов, а не заранее.
- **Промпты.** Отдельный набор «… · Locale» на базе промптов мешапа: пишутся по-английски (модели так стабильнее),
  требуют текст на `language`, стиль «как пишет местный журнал», единицы метрические, без цен и брендов магазинов,
  год 2027. Полный пересмотр промптов — отдельным этапом, как решил владелец.
- **Проверка качества** (`qualityCheck`) частично английская (стоп-слова, «Final Thoughts»): правила с английскими
  словами отключаются по флагу языка, структурные (число секций, объём, дубли H2) остаются.
- **Судья** `audit-text.ts` получает параметр языка: оценивает на языке статьи, отдельно отмечает кальку и ошибки
  согласования.

## 4. Публикация

Через существующий код WordPress (`src/lib/articles/wp/*`) по `SiteAccess` сайта. Карта категорий на языке —
в `LocSite` (ручная, по одной на нишу/поднишу: nehty, účesy, outfity…), без ИИ-выбора категории: именно он уронил
brown nails в /hair-color/ по-английски. Внутренние ссылки — только на статьи того же `LocSite`.

## 6. Риски

- Чешские/румынские объёмы малы: много ядер не наберут порог — лучше меньше тем с объёмом, чем перевод всего банка.
- Semrush через group-buy: лимиты юнитов и стабильность доступа не наши — адаптер объёмов позволяет уйти на DataForSEO (его баланс кончился 07.11, ошибка 40101).
- Discover не живёт на ключах так, как поиск: ключ нужен для заголовка и темы, но трафик даст подача (H1, обложка,
  свежесть). Заголовок на языке должен строить полировщик по правилам Discover, а не калькой с «Chic … 2027».
- Склейка ядер (шаг 4) уменьшает число статей на язык примерно на 15–25 % — закладывать в ёмкость сайтов.
