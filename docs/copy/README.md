# Article Copy (мешап статей)

Раздел `/pinterest/copy`, проект `copy`. Новые статьи для Pinterest (английский) из уже одобренных фото сервиса «Статьи»:
тратимся только на текст. Код статей не меняется, таблицы `Article`, `ArtPhoto`, `ArtPhotoCandidate` только читаются.

## Решения владельца (05–06.11.2026)

- Виды статей: **А** — то же ядро, новая формулировка, другой сайт; **Б** — новый узкий ключ, кадры подбираются по фактам из любых тем ниши. Начинаем с А.
- Сайты привязывает владелец в настройках инструмента (`CopySite`).
- Только уникальные темы: ядро, уже стоящее на сайте в любой формулировке, на этот сайт больше не идёт.
- Банк фото по умолчанию у каждой команды свой; общий включает только главный админ (`CopySettings.sharedBank`).
- Совпадение с любой одной существующей статьёй — не больше 30 % кадров; новая статья собирается из 3–4 старых.
- Резерв подмешивается обязательно, чем больше, тем лучше, с оценкой ИИ от 8.
- Около 25 фото в статье, число можно задать своё.
- Одно фото на одном сайте — до 3 раз, в одной статье — один раз.
- Текст пишется заново по сохранённым описаниям и фактам; описание кадра делается повторно, только если его нет.
- Файлы перезаливаются в медиатеку целевого сайта. Пины — обычным инструментом.
- Ниши не смешиваются: интерьер отдельно, женские (образы, волосы, ногти) отдельно.
- С 06.11.2026 резерв хранится ссылкой на источник (файл удалён, есть миниатюра, описание, факты); потеря части ссылок допустима.
- Другие языки — позже отдельным инструментом в Discovery.

## Этап 1 (сделан): карта ключей и запас

- `src/lib/copy/keys.ts` — разбор ключа: «Classy Almond Nails 2027» → ядро `almond nails`, формулировка `classy`; формула запаса `capacityByPhotos`.
- `src/lib/copy/build.ts` — `rebuildCopy()` пересобирает `CopyCore` целиком; `copyTick()` зовёт воркер раз в минуту (пересчёт по запросу с экрана и раз в 6 часов).
- `src/lib/copy/queries.ts`, `src/actions/copy.ts` — данные экранов и действия.
- Экраны: «Запас» (сводка по командам и нишам, таблица ядер), «Сайты и правила», карточка ядра.

Запас по ядру: статьи по N фото; из каждой старой статьи в новую идёт не больше `maxOverlapPct` кадров; остальное добирается резервом.
`capacity = min(по кадрам, свободные сайты)`. Это оценка сверху: лимит «до 3 раз на сайт» и нерабочие ссылки резерва проверяются при сборке.

## Этап 2 (сделан 06.11.2026): автосборка

Решение владельца: «всё должно работать автоматически». Ручного подбора и предпросмотра нет.

- `src/lib/copy/auto.ts` — `copyAutoTick()` (воркер, раз в минуту, до 2 статей за проход): по привязанным сайтам в пределах
  `dailyPerSite` выбирает ядро (ниши, которые сайт реально ведёт; не было на сайте; не собиралось за сутки), первую свободную
  формулировку (`pickModifier`: стандартные, потом запасные), кадры и создаёт обычную `Article` на этапе `plan` + `ArtPhoto` + `CopyArticle`.
- Ключ = ключ самого свежего донора с другой приставкой (`swapModifier`), год остаётся как у донора.
- Кадры: доля резерва `reservePct` (скачивается по ссылке источника, не скачалось — берётся следующий), остальное из опубликованных
  по кругу между донорами; с любой существующей статьёй не больше `maxOverlapPct`, на сайте фото не больше `maxPerSite` раз,
  меньше `minPhotos` — ядро откладывается на 6 часов.
- Статья идёт обычным конвейером статей: план → текст → сборка → публикация. `cursor.reviewApproved = true` — без модерации статьи;
  при `reviewBeforePublish` статья ждёт в модерации статей. Факты темы строятся без ИИ, тренд-бриф берётся у донора.
- Сценарий и автор (ключи ИИ) — как у статьи-донора той же команды.
- Не собирается: ядра из одного слова (там темой была приставка); пустые сайты без указанной ниши.
- Экран «Собранные статьи» (`/pinterest/copy/articles`), блок «Автосборка» в «Сайты и правила». По умолчанию автосборка выключена.
- Вручную: `scripts/copy/plan.ts --site <сайт> [--core …] [--n 3]` — показать подбор; `--create [--review]` — создать одну статью.

Автосборка не собирает на сайт, если у него выключено «Написание» (сайт, команда или общий выключатель в «Статьях» — те же, что смотрит очередь), и если на сайте уже лежит `max(4, 2 × суточная норма)` собранных, но не дописанных статей. Причины видны в заметке блока «Автосборка». Проверка 06.11: статья из 25 кадров прошла план → публикация за ≈80 с и $0.015 (thefreshstyle.com, остановлена на модерации).

## Этап 3 (сделан 07.11.2026): партии и частотность

Владелец 07.11: «запускать не нормами в сутки, а партиями: сегодня 300 статей — 100 ногти, 100 волосы, 100 одежда, часть ВЧ/СЧ/НЧ»; банк — общий для всех команд сразу.

- **Общий банк** (`CopySettings.sharedBank`, включён 07.11): карта ядер одна на всех, строки `CopyCore.teamId = "shared"` (`SHARED_TEAM` в `keys.ts`); раньше при общем банке строки оставались по командам и дашборд утраивал цифры.
- **Частотность ядра** (`CopyCore.volume`, `volClass`): при пересчёте карты ключи «Подбора ключей» (`KwKeyword.volume`, Ads Manager США) сводятся к ядрам тем же `splitKeyword`, берётся максимум. Классы: ВЧ ≥ 30 000, СЧ 10–30 000, НЧ 3 000–10 000, мелкие < 3 000, null — ключа там нет. Покрытие 07.11: волосы 96 %, ногти 90 %, одежда 95 % запаса по статьям; интерьер сначала 0 % — 07.11 в «Подбор ключей» загружены (ниша `interior`, только частотность, `scripts/keywords/import-decor.ts`): 1 433 декор-ключа из вкладки Decor (≥ 1000) и рождественские замеры 31.10 (316 декор + 158 женских, ≥ 500; сняты не в сезон, поэтому занижены — классы рождественских тем условны). Интерьерный запас сейчас почти целиком рождественский.
- **Партии** (`src/lib/copy/batch.ts`, экран «Партии»): форма — сайты галочками (только привязанные), таблица квот «ниша × ВЧ/СЧ/НЧ/любые», слово-фильтр по ядру, число фото, проверка перед публикацией. `planBatch` сразу раскладывает темы по сайтам: ядра по убыванию резерва, каждое ядро в партии один раз, сайт — с наименьшим числом статей в партии, которому тема подходит (группа ниш, ниши сайта, ядра на сайте ещё нет, в т. ч. по `CopyArticle`). Недобор по клеткам и сайты с выключенным «Написанием» — в заметке партии. Пункты — `CopyBatchItem`; воркер `copyBatchTick` раз в минуту собирает до 15 пунктов (`buildCopyArticle` с числом фото партии, `CopyArticle.batchId`, запуск в «Статьях» называется `Article Copy · <партия>`). Пауза / продолжить / отменить остаток — с экрана партии.
- Стоимость текста ≈ $0.015 на статью из 25 фото (обычная статья $0.059, из них $0.045 — поиск и оценка фото). Форма показывает оценку.
- Проверка планировщика без сборки: `scripts/copy/batch-test.ts` (создаёт партию на паузе, печатает раскладку, удаляет).

## Этап 4 (07.11.2026): доноры/получатели, лимит кадров, разнообразие, таблица публикаций

Запросы владельца 07.11 после теста на lightstyleideas.com (10 статей опубликованы, $0.011–0.017 за статью):
- **Доноры и получатели** — `CopySite.donor` (по умолчанию все сайты доноры; строка CopySite нужна, только если сайт получатель или не донор). Мешап-статьи (есть в CopyArticle) донорами не бывают: их кадры в пул не идут ни в `rebuildCopy`, ни в `buildCopyArticle`. Экран «Сайты и правила» — таблица с двумя галочками.
- **Лимит использований кадра** — `CopySettings.maxUsesTotal` (3): кадр во всех статьях вообще, исходная считается; `maxPerSite` остался. Сводка по кадрам считается при пересчёте карты в `CopySettings.stats` ({niches: {published, reserve, uses1, uses2, uses3, usesLeft}}) и показана на «Запасе» карточкой «Кадры».
- **Партии**: диапазон фото `photos`–`photosMax` (число случайное на статью), разнообразие `maxPerWord` — слово ядра без «головных» (`clusterWords` в keys.ts) не чаще N раз на партию; на странице партии — кластеры тем (`clusterOf` = первое содержательное слово). Формулировка теперь случайная из свободных стандартных (потом запасных); год всегда в конце ключа.
- **Google-таблица публикаций** — `CopySettings.sheetUrl`; `src/lib/copy/sheet.ts` (`copySheetTick`, раз в 5 минут) дописывает опубликованные мешап-статьи на вкладку = домен сайта (создаёт вкладку с заголовком): Keyword | Niche | Class | Volume | Publish URL | Data Publish | Photos | Batch | Site; `CopyArticle.sheetAt`. Таблице нужен доступ «Редактор» для сервисного аккаунта «Статей» (ArtSettings.sheetsEmail).
- Аудит соответствия фото и текста: `scripts/copy/audit-photos.ts --batch <id>` (модель зрения смотрит кадр + заголовок + текст секции → yes/partial/no).
- Добавление сайта из консоли: `scripts/articles/add-site.ts` (пароль приложения через `WP_APP_PASSWORD`).

### Как запустить партию из консоли (для Claude или оператора)
```
sudo -u zewex_tools_usr -H npx tsx scripts/copy/batch-test.ts --site lightstyleideas.com   --quota nails:hi=49,mid=57,low=57 --quota hair:hi=49,mid=57,low=57 --quota outfits:hi=49,mid=57,low=57   --year 2027 --photos 20 --photos-max 35 --max-per-word 3 --publish --run --name "lightstyleideas · 490"
```
Без `--run` партия создаётся на паузе и удаляется (сухой прогон раскладки); `--keep` — оставить на паузе; `--publish` — без модерации; `--season` — разрешить сезонные темы.

### Аудит соответствия фото и текста (07.11.2026)
`scripts/copy/audit-photos.ts` по 10 тестовым статьям: 187 секций «да», 40 «частично», 23 «нет» из 250 (контроль на двух обычных статьях: 38 / 4 / 4 из 46). Две причины:
1. Планировщик (`rp_photo_plan`) иногда возвращает `photo_n` со сдвигом — заголовки садятся на чужие фото (в «Classy Nail Art» 4 секции по кругу). Исправлено в `worker/articles/stages/plan.ts`: `repairPhotoMapping` сверяет план секции с описанием её фото по словам и меняет фото местами у пар, которым явно лучше подходят фото друг друга (на тестовой статье нашёл ровно те 4, на остальных — 0). Работает для всех статей, не только мешапа.
2. Часть описаний в банке относится к другому кадру (пачечное описание по 8 фото у доноров). Для мешапа описания и факты донора больше не переносятся: `buildCopyArticle` пишет фото без них, а этап плана описывает каждый файл заново по одному (`describeLatePhotos({ single: true })`, ~$0.01 на статью). При первом прогоне половина одиночных описаний терялась: flash-lite дописывает мусор после JSON — починено в `parseModelJson`/`parseJsonLenient` (первый сбалансированный объект). Проверка на 2 статьях после первой правки: 0 «нет» из 50.

## Этап 5 (07.11.2026): свои промпты мешапа

Владелец: «доработать промпты по мешапу, чтобы тексты были лучше и немного отличались от наших; H2 тоже другие».
- Тексты шагов лежат в репозитории: `prompts/copy/<ниша>-<stageKey>.txt` (ногти, волосы, одежда; шаги rp_photo_plan, rp_section_plan, stage_7_writer_system, stage_7_writer_user, stage_7_intro_outro). Формат файла: `===SYSTEM===` / `===TEXT===`.
- `scripts/copy/apply-prompts.ts` клонирует боевой набор реальных фото ниши в набор «… · Article Copy», подменяет шаги файлами, создаёт/обновляет сценарий `ArtRecipe.forCopy = true` (№10 ногти, №11 волосы, №12 одежда; модель планирования gemini-2.5-flash вместо lite). Повторный запуск = обновить промпты из файлов. `buildCopyArticle` берёт сценарий forCopy ниши, если он есть.
- Чем отличаются от оригинала: правило доказательств (длина, форма, оттенок, чёлка, обувь — только если есть в описании файла; «нет длины в фактах» → слова о длине нет), H2 в sentence case и никогда не начинаются с формы/длины (ведут с детали или ситуации читателя), в каждой секции «skip it if», «салонная» реплика другой формулировкой («At the salon, say:», «Tell your stylist:», «To rebuild it, look for»), вступление с ситуации читателя вместо тренд-факта, заключение «pick by» списком.
- Аудиты: `scripts/copy/audit-photos.ts` (фото ↔ секция) и `scripts/copy/audit-text.ts` (судья по всему тексту: конкретика, повторы, вода, H2, связность, риск неточностей, запрещённые слова, одинаковые зачины).

### Итерация v1 → v2 (07.11.2026)
Тест v1 (партия «lightstyleideas · промпты Copy v1», 10 статей: ногти 2, цвет 2, стрижки 2, причёски 2, одежда 2). Фото-аудит: 15 «нет» из 254 (6 %). Судья по тексту: overall 4–6/10, главные претензии — формульные H2 (Title Case дотягивался кодом в assemble), «Tell your stylist» и «To rebuild it» в каждой секции, одинаковые зачины («This works for…»), выдуманная длина «mid-back» (описатель кадра гадал по обрезанному фото), коллажи из нескольких женщин, застрявшие слова polished / reads as / sophisticated.
v2: `polishHeading({ keepHeadingCase })` для мешапа; `COPY_RULES` в одиночном описании (длина только при видимых концах, подсветка только при явных прядях, префикс «Collage:») и повтор на gemini-2.5-flash при сбое; план исключает коллажи и неописанные кадры (если остаётся ≥ 15); промпты: салонная/магазинная реплика ≤ половины секций с ротацией формулировок, skip_if ≤ 6 секций, уникальное первое слово секции и запрет This/The/That/A, расширенный бан-лист, правила разнообразия H2, естественная вставка ключа во вступлении. Стоимость мешап-статьи с новыми промптами ≈ $0.03–0.05 (описание кадров + план на 2.5-flash + 20–30 фото).

### Результат v2 (партия «lightstyleideas · промпты Copy v2», 10 статей)
Фото-аудит: 29 «нет» из 260 (11 %), хуже v1 — почти все в волосах: описатель кадра по-прежнему называет длину (collarbone, mid-back) по обрезанному фото, и в ядро «balayage hair» попали кадры кудрявых волос без балаяжа; один коллаж («three women») не пойман регулярным выражением. Судья по тексту: overall 5/10 у всех (v1: 4–6) — писатель deepseek-v4-flash игнорирует часть правил: «Ask your stylist for» и реплики почти в каждой секции, зачины «This style works best…», слова polished / sophisticated / reads as; H2 стали sentence case, но по структуре всё ещё «цвет + стрижка + деталь».
Вывод: промптами потолок достигнут; дальше нужны (1) A/B модели писателя для мешапа (gemini-2.5-flash или claude vs deepseek) на 4 статьях, (2) детерминированная чистка: вырезать слова длины из описаний волос в copy-режиме и расширить список штампов `polish.ts` для copy, (3) фильтр кадров по теме при сборке (кадр «balayage» должен содержать слово из ядра в описании).

## Планировщик (07.11.2026)
`/pinterest/copy/plan` (`src/lib/copy/plan.ts`): ёмкость по нишам × ВЧ/СЧ/НЧ (темы и статьи с учётом бюджета кадров), по каждому сайту свободные темы и «можно дописать» с кнопкой «Партия» (`createTopUpBatch`: 30 % ВЧ, ниши в пропорции сайта, самые частотные темы, 20–30 фото, следующий год, без сезонных, публикация сразу), калькулятор новых сайтов (группы «N сайтов × M статей», раскладка 30/35/35, остаток).
