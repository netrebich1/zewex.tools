# Zewex Tools — заметки для Claude

Внутренний портал инструментов на https://zewex.tools. Общение с владельцем на русском, он не технический: команды давать пошагово.

## Стек и структура
- Next.js 15 (App Router, `output: standalone`), React 19, Tailwind 4, Prisma 6, MariaDB.
- `src/lib/resolve.ts` — выбор правила для слота (USER_PROJECT → TEAM_PROJECT → PROJECT → TEAM → GLOBAL).
- `src/lib/adapters.ts` — вызовы провайдеров (OpenAI-совместимые, DataForSEO, SerpAPI); `src/lib/run.ts` — прокси + журнал расхода.
- `src/actions/*.ts` — все мутации (server actions), формы через `components/ActionForm.tsx`.
- `prisma/seed.mjs` — провайдеры, модели Perplexity, разделы (идемпотентен).
- Tailwind 4: нельзя `@apply` своих классов, только встроенные утилиты.

## Сборка и деплой
На Mac нет Node: локально только редактируем, собираем на сервере.
- Деплой одной командой: `./deploy/deploy.sh` (rsync → npm install → prisma db push → seed → build → systemd + nginx).
- Проверка типов на сервере: `ssh -i ~/.ssh/fastvps_ed25519 root@159.69.234.194 'cd /var/www/zewex_tools_usr/data/app && sudo -u zewex_tools_usr npx tsc --noEmit'`.
- Логи: `journalctl -u zewex-tools -n 100`. Сервис слушает 127.0.0.1:3100.
- Секреты только в `.env` на сервере (не в git). Никогда не печатать APP_ENCRYPTION_KEY и пароли в чат.
- Репозиторий: `git@github.com:netrebich1/zewex.tools.git`, ветка `main`, пуш через deploy key.

## Pinterest Pins (сервис пинов) и воркер
- Страницы `src/app/(app)/pinterest/pins/*`, действия `src/actions/pins.ts`, библиотеки `src/lib/pins/*` (ai, stages, prompts, plan, texts, wp, schedule, export, canvas). Рецепт сайта и константы — `src/lib/pins/types.ts`.
- Фоновая работа только в воркере `worker/` (systemd `zewex-worker`, `tsx worker/index.ts`): очередь `PinJob`, этапы `worker/stages/*`, реестр `worker/stages/index.ts` — при правках проверять, что все этапы зарегистрированы.
- ИИ-стили (`src/data/pins/ai-styles.json`): у стиля может быть `niches` (decor, interior…) — фильтр «Ниша» в `AiStylePicker`, подписи `STYLE_NICHE_LABELS` в `prompts/aiStyles.ts`. Новогодняя линия для декора/интерьера: 12 направлений × 3 подачи (`ny-decor-*`, категория newyear), добавляются `scripts/pins/add-newyear-decor-styles.py` (идемпотентно). Примеры: `scripts/pins/gen-style-examples.ts --category=newyear --styles=<база> --keyword=… --niche=decor --season=winter` (≈$0.04 за картинку medium).
- Canvas v8 (2026-10-15): `StyleSpec.title` умеет `minSize/maxSize/leading` (постер до 200 px), `outline` (stroke/echo/hollow), `shadow`, `emphasis` (часть слов крупнее/другим шрифтом/цветом, в т.ч. рукописным `fonts.script`; при 7+ словах отключается), `align: left` работает; `photo: {style: polaroid|card, tone: duotone|mono|warm, shape: arch, overlap}`, `ringBadge`, `rule`, `grain` рисуется, `color: photo-tint-dark`, `plate-glass-*` = размытое стекло (`host.snapshot`). Всё это `CanvasRecipe.fx` (`toRecipe`). Зона `middle` — заголовок между рядами фото. Наборы шрифтов несут `scripts` (латинские наборы не идут на кириллицу: `toRecipe(spec, seed, n, {script})`, воркер передаёт `scriptForLanguage`) и `leading`. Свои стили: 20 `zx:*` + 22 `zx27:*` в `curated.ts`; `seedCuratedStyles` обновляет существующие строки каталога при изменении спецификации в коде (превью сбрасывается, утверждение сохраняется) — запускается кнопкой «Обновить превью» (harvest). Хуки Canvas: лимит 44 знака, повисшие предлоги снимаются, резаные хуки идут последними. Отладка новых стилей без базы: `render-style.ts <out> x --spec=<json> --title="…"`.
- Canvas рендерится на сервере (`@napi-rs/canvas`), шрифты в `storage/pins/fonts` (скрипт `scripts/pins/fetch-fonts.mjs`). Каталог стилей: `canvas/catalog.ts` (сбор из легаси + свои стили `canvas/curated.ts` + сочные палитры `canvas/paletteLibrary.ts` + наборы шрифтов `canvas/fontSets.ts`; у стиля 1–4 палитры и до 4 альтернативных наборов шрифтов, seed выбирает; старые строки каталога догоняются `upgradeCatalogSpecs` в `previews` при harvest). Профиль акцента для обрезки (`crop.ts`) задаётся в `worker/stages/canvas.ts` через `guessAccent(ниша, ключ)`. Кадрирование фото: рамка главного объекта от модели со зрением (`canvas/subject.ts`, слот `text_fast` = gemini-2.5-flash, формат детекции `box_2d` 0–1000 БЕЗ json-режима — в json-режиме Gemini отдаёт рамку на весь кадр; кэш `pins/photos/<sha1>.subject.json`, ~$0.0007/фото), `drawSmartCover({subject})` накрывает рамку и держит её верх, если не влезает; без рамки — карта энергии как в легаси (центрирование по боксу акцента). Перерисовать существующий пин текущим кодом: `scripts/pins/render-item.ts <outDir> <itemId…>` в `/root/zewex-check`. Отладочный рендер без базы изменений: `scripts/pins/render-style.ts` + `scripts/pins/contact-sheet.mjs` (запускать в `/root/zewex-check` с `PINS_STORAGE_DIR` на копию). Файлы сервиса: `/var/www/zewex_tools_usr/data/storage/pins`, отдаются nginx как `/files/`.
- Проверка типов воркера: `npx tsc --noEmit -p tsconfig.worker.json`. Без деплоя проверять в копии `/root/zewex-check` на сервере.
- Три уровня настроек. Система `/sites` (`SiteAccess` + `SiteAccessTeam` доп. команды + `SiteAccessViewer` видимость сотрудникам; проверки — `src/lib/sites/access.ts`: `canAccessPinSite`, `pinSiteWhere`, `pinRunWhere`, `canSeeAccess`; `canAccessTeam` только для командных сущностей). Сервис `/pinterest/pins/sites/[id]?tab=settings` (`PinsSiteSettings`: имя, ниша, доски, наборы ИИ, Canvas-стили, Pinora, язык, аудитория, цвет, домен ссылок — в `PinSite.recipe`). Прогон (`PinRun.settings`): источник статей `pages`, mix, photosMode, photoLinkPercent, проценты текстов, numberSource, schedule, multiBoard — форма `RecipeFields scope="run"`, значения по умолчанию из последнего прогона сайта (`runDefaultsFrom`). `recipeFromForm` меняет только присланные группы полей (маркеры `setsPresent`, `multiBoardPresent`, `pagesSkipUsedPresent`).
- Источник статей: `Recipe.pages` (`PagesSource`): вручную или из WordPress по REST API (тип записей, категории/исключение, период «любые / за N дней / с даты по дату», лимит ≤500, пропуск использованных). Поля — `components/pins/PagesSourceFields.tsx` (шаг 3 нового прогона), подбор при запуске без ссылок — `sitePostsBySource` в `lib/pins/wp/posts.ts` из `launchRun`.
- Лимит сайта: `pinsPerDay` — пины ЭТОГО прогона в день; пины других прогонов на те же даты плюсуются, общий потолок 100/день на сайт (`MAX_PINS_PER_DAY`) жёсткий. Лишнее уходит на ближайшие свободные дни; `scheduleItems` сравнивает с раскладкой без лимита (`ignoreSiteLimit`) и отдаёт `limitReport`, этап `schedule` пишет `settings.scheduleReport`, `explainSchedule` показывает жёлтую плашку «перенесено N и почему». Выгрузка дня — один файл на сайт по всем прогонам; все сайты на сегодня — `todayAllZip`, `GET /api/pins/export/today`, выделенная ссылка в `PinsNav`.
- Расписание прогона (`schedule/plan.ts`, `scheduleItems`): два режима `schedule.dailyMode` — `fixed` (строго pinsPerDay в день, окно растёт само) и `dates` (равномерно от startFrom до lastDate, потолок 100/день, остаток после lastDate). День наполняется до нормы в три прохода: желаемая дата наступила и предпочтения статьи соблюдены → будущие подтягиваем вперёд → ослабляем «со статьи в день»; порядок пинов внутри статьи не ломается. Первый пин/шаг/«со статьи в день» — мягкие предпочтения (UI `ScheduleModeFields.tsx`). Симуляция: `scripts/pins/sched-test.ts` в `/root/zewex-check`.
- Год на пинах и в текстах: доля «Год» (`text.percents.year`) действует на надпись на пине, заголовок и описание одним жребием (`itemYear` в `prompts/elements.ts`: Canvas — `styleParams.tags`, Pinora — `styleParams.yearEnabled`, остальное — `decideElements(id)`); тексты получают `YEAR` по элементу, `applyYear` в `texts/rules.ts` правит чужие годы, дописывает год в заголовок или вырезает годы. Особые годы прогона `text.yearRules` (галочка «Другой год для отдельных тем», `YearRulesFields.tsx`): слово в ключе/заголовке/H1/теме статьи → год правила (`pinYearFor`); выключенные правила сохраняются, но не действуют.
- Фото статьи: `Recipe.photosMode` = `auto` (по умолчанию; старое "all" читается как auto) | `sections` | `featured_only`; `featuredOnlyFor(mode, page.niche, site.niche)` — в auto кулинарные статьи (`niche = cooking`) берут только миниатюру. Миниатюра в `worker/stages/photos.ts`: WordPress REST `featuredImageByUrl` (по slug, posts → pages) → og:image → первое фото.
- Видимость сайтов (правило владельца 2026-10-12): в команде сотрудник видит только СВОИ сайты — где он в `SiteAccessViewer`; пустой список НЕ значит «вся команда». Всё видят ADMIN / право `sites: all`, сайты своей команды — её лидер. `saveSiteAccess` оставляет автора в списке видящих (кроме админа/лидера). Прогоны и модерация наследуют видимость сайта. Проверка «что видит сотрудник» — скрипт по образцу из истории (`pinSiteWhere`, `pinRunWhere`, `moderationCounts` с собранным `CurrentUser`).
- Удаление прогона (`deleteRun`): каскадом пины/страницы/задачи + `PinUrlHistory` этого прогона (статьи снова «не использованы») + папка картинок; запас по дням и выгрузка считаются из пинов, поэтому обновляются сами (`deleteRunAction` делает revalidate). Подтверждение с последствиями — `runDeleteImpact` + `deleteConfirmText`; кнопки на странице прогона и в списке прогонов. Медиа в WordPress не удаляются.
- Параллельность: ИИ-картинки 15 на прогон (`PINS_IMAGE_CONCURRENCY`, этап `images`) и не больше 15 на ключ по всем прогонам (`DEFAULT_LIMITS.IMAGE` в `ai/limiter.ts`); Canvas 3 одновременно (`PINS_CANVAS_CONCURRENCY`, `runQueue` в `worker/stages/canvas.ts`, фото и рамки объектов на одно фото — один раз). Сервер 2 ядра: Canvas выше 3 не поднимать. До 2026-10-14 было 6 и 1 (~22 ИИ/мин, ~17 Canvas/мин).
- Размер прогона: до `MAX_RUN_PAGES` = 3000 статей (types.ts; форма, разбор формы, `createRun`, `sitePosts`). Server actions принимают до 8 МБ (`next.config.ts`). Этап `schedule` пишет даты пачками по 500 через `UPDATE … CASE` (30 000 пинов за раз); расписание 30 000 пинов считается ~3 с.
- Новый прогон, статьи из WordPress: одна галочка `pages.skipUsed` управляет и видимостью, и выбором (отдельной «скрыть использованные» больше нет); если список показан и ничего не выбрано, форма шлёт `urlsExplicit=1` и `launchRun` отказывает, а не подбирает молча.
- Проблемы прогона: `lib/pins/runs/problems.ts` (чистые функции `explainItemError` по `errorKind`, `explainBlocked` по `blockedReason`, `explainPageErrors`, `healthOf`, `verdict`). critical = прогон стоит (BLOCKED/FAILED, auth, no_credits) → красная плашка; warning = часть пинов пропущена (safety, bad_request, повторы, статьи) → жёлтая. `RunStatusView.problems/health`, `problemsForRuns` для списка; компонент `ProblemsDetails` (раскрывающаяся плашка с тезисами) на «Сегодня», в истории и на странице прогона. Новый вид ошибки добавлять в `explainItemError`.
- Пост-модерация: вкладка `/pinterest/pins/moderation?view=post` — одобренные пины (`kind=pin`, `postReviewedAt=null`, дата сегодня/позже или нет), та же сетка `ModerationGrid post`; `applyDecisions(..., {post:true})` ставит `postReviewedAt`, отклонённые получают `rejectReason=post_moderation` и уходят из выгрузки/запаса. Очередь — `queueWhere(view)` в `runs/moderation.ts`.
- Страница «Стили» (`/pinterest/pins/styles`): сайт переключается сразу (`StylesSiteSwitch`, router.push), вкладки получают `key={site.id}`; набор редактируется по кнопке «Изменить» в таблице → `?edit=<setId>#gallery` → `AiStylePicker initialEdit` (выбор из набора, фильтр «только выбранные»).
- Инструкция для сотрудников: `/pinterest/pins/guide` (вкладки «Основная» и `?tab=cooking`), шаги и подписи к цифрам — массивы `MAIN`/`COOKING` в `guide/page.tsx`. Скриншоты в хранилище `pins/guide/<имя>.jpg`, загружаются админом через `POST /api/pins/guide/shot?name=`; снимаются из браузера библиотекой html-to-image (cdnjs) с оранжевыми цифрами-пометками, перед снимком логин WordPress подменяется, длинные списки обрезаются.
- Выгрузка: файл дня `DD_MM_YYYY_Site_<пинов>.csv` (`export/pinterest.ts` `fileName`); «выгрузить все сформированные для сайта» — `siteAllZip` в `export/service.ts`, `GET /api/pins/export/all?site=` → ZIP по CSV на день с сегодняшнего (кнопки: страница выгрузки, действия прогона, шапка сайта в инструменте).
- Прогоны: история `/pinterest/pins/runs` (фильтры сайт/статус), страница прогона с вкладками Обзор / Страницы и пины / Расписание / Журнал этапов / Настройки (`components/pins/RunDetails.tsx`). Автоуборка: `lib/pins/runs/cleanup.ts` (`purgeOldRuns`, 90 дней после последнего запланированного пина, иначе после последнего изменения) — вызывается из `worker/cron.ts` раз в сутки.
- Ключи ИИ назначаются сервисам/командам на странице ключа. Сайты — общий раздел `/sites`: сайт = `SiteAccess` (REST API WordPress, команды, сервисы, видимость) + привязанный `PinSite` (`wpConnectionId`), настройки которого живут в сервисе (`components/sites/PinsRecipeForm.tsx` → `PinsSiteSettings`). `/access` редиректит на `/sites`. Удаление сайта — `deleteSiteAccess` (`actions/access.ts`): только с названием сайта в поле `confirm` (двухшаговая форма `components/sites/DeleteSiteForm.tsx`), удаляет доступ, `PinSite` с прогонами и файлами, `ArtSite` со статьями и файлами; при работе в процессе (прогон QUEUED/RUNNING, статья RUNNING/PUBLISHING) отказывает. Что уйдёт — `siteDeletionImpact` в `lib/sites/delete.ts`. Отключить инструмент от сайта и подключить снова — `setSiteToolActive` (`actions/access.ts`, строка `ToolRow` на `/sites/[id]`): это `isActive` у `PinSite`/`ArtSite` (архив), данные не удаляются; отказ, пока идут прогоны QUEUED/RUNNING или статьи RUNNING/PUBLISHING; снова подключить можно, только если инструмент отмечен в `SiteAccess.projects`. На сервере нет IPv6: `NODE_OPTIONS=--dns-result-order=ipv4first` в unit-файлах.

## DeepL Articler (раздел Discovery, проект `deepl`)
- Пакетная адаптация статей WP: перевод DeepL по цепочке до 3 шагов (UK → EN-GB → DE → UK) → H2 → постредактура → добор SEO-ключей → (публикация). Перенос «article-jumble-maker» (Lovable) без мешапа/вступления/мета/перелива картинок/обложек — мешап позже отдельным инструментом.
- Страницы `src/app/(app)/discovery/deepl/*` (список, `new`, `runs/[id]`, `keys`, `settings`), действия `actions/deepl.ts`, API `/api/deepl/{posts,categories,jobs/[id],items/[id]}`, компоненты `components/deepl/*`, библиотеки `src/lib/deepl/*`: `html.ts` (чистые функции оригинала: защита `<a>`/`<img>`/шорткодов/iframe тегом `<x-ph i="N">`, кавычки, целостность, ключи; тест `npx tsx scripts/deepl/selftest.ts`), `deepl.ts` (пул ключей, кэш `DeeplCache`, параллельные фрагменты), `edit.ts` (OpenRouter через `runSlot`, слот `text_main`; постредактура, H2 — `parseHeadings` берёт «РЕКОМЕНДОВАНИЙ НАБІР»), `process.ts` (одна статья: этапы, снимки, возобновление по префиксу готовых снимков, откат плохого этапа), `jobs.ts` (очередь, стоп/продолжить/повтор, публикация, откат), `wp.ts` (сайты из `/sites`, где отмечен `deepl` или список сервисов пуст; посты по статусу и дате, `context=edit`).
- Ключи DeepL — ТОЛЬКО внутри инструмента (правило владельца 2026-10-15: не в общем разделе «Ключи» портала), вкладка `/discovery/deepl/keys`, `DeeplKey`; управляет любой, кому открыт инструмент. Как в исходном сервисе: у ключа лимит символов — свой (`limitManual`, «Обновить расход» его не трогает; «задать лимит всем») или из DeepL `/v2/usage`; учёт = видимый текст ×1.15 после каждого ответа; остаток проверяется ДО запроса; 456/403/401 выключают ключ, при обновлении расхода ключ, выключенный по 456, включается, если остаток появился. Ключи работают параллельно (`takeKey` в `deepl.ts`: самый свободный ключ, `DEEPL_PER_KEY_CONCURRENCY`=2 запроса на ключ, при равенстве — по порядку). Массовое добавление `addDeeplKeys` (UUID + `:fx` из любого текста, название — текст перед ключом). ## Трафик сайтов (раздел Аналитика, проект `analytics`) — Google Analytics 4
- Кабинет поверх GA4 для всех Google-аккаунтов владельца: `/analytics` (обзор: KPI, график, таблица сайтов, каналы/страны/устройства, часы), `/analytics/sites/[id]` (сайт: вкладки страницы/источники/география/устройства/часы), `/analytics/pages` (страницы всех сайтов: поиск по адресу и заголовку, фильтр сайт/группа, сортировка рост/падение), `/analytics/settings` (аккаунты, переключатели сайтов, группы). Инструкция по Google Cloud — `docs/analytics/README.md`.
- Аккаунты Google — внутри инструмента (`GaAccount`: OAuth refresh token или JSON сервисного аккаунта, зашифрованы), не в общем разделе «Ключи». OAuth: `GOOGLE_OAUTH_CLIENT_ID/SECRET` в `.env`, `/api/analytics/oauth/{start,callback}` (state в cookie), scope analytics.readonly. Видимость: автор аккаунта + ADMIN (`accountWhere`/`propertyWhere`/`groupWhere` в `lib/analytics/access.ts`).
- Данные живут в своей базе: `GaDaily` (итоги дня), `GaHourly`, `GaPageDaily` (топ 1000 страниц/день, ключ sha1 пути, `normalizePath` без хвостового слэша), `GaDimDaily` (kind: channel/source/country/device/referrer). Синхронизация — воркер `worker/analytics.ts` → `lib/analytics/sync.ts` `syncProperty`: каждый час перечитывает 3 дня, историю докачивает порциями (`BACKFILL_DAYS` в `types.ts`: 400/400/90/120 дней; страницы по 10 дней за проход), `syncState.done` — история загружена. Ошибка авторизации → `GaAccount.status=ERROR`, сайты аккаунта не синхронизируются до переподключения. Отказы = 1 − engaged/sessions, время = engagementSec/sessions (`derive` в `query.ts`), конверсии = `keyEvents`.
- Период из адреса (`lib/analytics/period.ts` `parseRange`: `p`, `from`, `to`, `cmp` prev/year/none, `g` hour/day/week/month, `m`), «сегодня» — пояс свойства или `GA_DEFAULT_TZ` (Europe/Kyiv). Выборки — `query.ts` (raw SQL, `CAST(... AS DOUBLE)`), сравнение выравнивается по индексу. Realtime («сейчас на сайте») — `/api/analytics/realtime?ids=`, кэш минута. CSV — `/api/analytics/export?kind=sites|pages`. Графики: цвета `--viz-1`/`--viz-prev` в `globals.css`, одна ось, сравнение пунктиром (`TimeChart.tsx`).

## Права сотрудников и ключи
- Админ (`User.role = ADMIN`) может всё. У сотрудника набор `Permissions` в `User.permissions` (JSON, null = по умолчанию): `usage` own/team/all, `keysView` none/own/team/all, `keysCreate` none/personal/team/all, `keysAssign` none/team/all, `teams` view/manage/all, `providers` none/view/manage, `sites` team/all, `balances`, `users` none/view. Всё в `src/lib/permissions.ts` (типы, профили «Сотрудник / Лидер команды / Менеджер», `PERMISSION_FIELDS` для формы, чистые проверки `canViewKey`, `keyWhere`, `canManageKey`, `assignScope`, `canAssignGlobal`, `keyFitsRule`, `canDeleteBinding`, `canManageTeam`, `usageWhere`, `seesAllSites`, …). `CurrentUser.perms` считается в `getCurrentUser`; меню `Shell` и `/api/balances` фильтруются по правам. Лидер команды (`TeamMember.role = LEAD`) всегда имеет уровень «команда» в своей команде поверх личных прав.
- Инструменты сотрудника: `Permissions.tools` = `"all"` или список slug проектов (по умолчанию пусто — ни одного), галочки `components/users/ToolsAccessFields.tsx` на `/users` и `/users/[id]`. Закрытие в одном месте: middleware кладёт путь запроса в заголовок `x-zx-path` (`lib/requestPath.ts`), `requireUser`/`getCurrentUser` в `lib/auth.ts` по `Project.url` и `/api/<slug>` определяют инструмент и не пускают (`/?denied=1` или 401). Новому инструменту нужен `url` в сиде и API под `/api/<slug>/…`, тогда он закрывается сам. Плюс `toolWhere` на главной, `canUseTool` в `/projects/[slug]` и `/api/run`. Разделы «Команды» и «Расход» у сотрудника по умолчанию скрыты (`teams: "none"`, `usage: "none"`; `canViewTeams`, `teamWhere`, `canViewUsage`), лидер свою команду и её расход видит.
- Главные админы (владелец из `ALLOWED_REGISTRATION_EMAILS` всегда + `User.superAdmin`, ставит только владелец на `/users/[id]`): переключатель «Админ / Сотрудник» у аватарки (`Session.memberView` → роль MEMBER, его команды, права из его `User.permissions`; не сохранены — по умолчанию со всеми инструментами) и вход в кабинет любого активного сотрудника (`Session.actAsUserId`, меню под аватаркой или кнопка на `/users/[id]`). Всё в `getCurrentUser` (`lib/auth.ts`), поэтому подмена действует во всех страницах, действиях и API; настоящий вошедший — `realSession()`. Флаги живут в сессии главного админа: вернуться может только он, у сотрудника ничего не меняется; в кабинет главного админа войти нельзя. Действия — `actions/viewAs.ts`, UI — `components/ViewAs.tsx`, цвет шапки — `.view-member` (синий) / `.view-as` (фиолетовый) в `globals.css`. Действия в чужом кабинете пишутся в журнал расхода от имени сотрудника; входы и выходы — строка `[view-as]` в `journalctl -u zewex-tools`.
- Остаток на ключе вручную (OpenAI и другие LLM без баланса по API): `ApiKey.balanceUsd/balanceAt`, действие `setKeyBalance` (вписать заново / прибавить пополнение), расчёт `manualBalances` в `lib/balances.ts` = сумма − расход по `UsageLog` через ключ с момента ввода (все инструменты и команды; стоимость — оценка по ценам моделей). Балансы в шапке — право `balances`: `none` / `own` (по умолчанию: только ключи, на которых сотрудник работает по правилам своих команд или личным в открытых ему инструментах; общие ключи сервиса уровня PROJECT/GLOBAL не показываются) / `all` (все провайдеры, как у админа): `myKeyBalances` → `/api/balances/mine` → `HeaderBalances mine`.
- Смена владельца ключа («Чей ключ» на странице ключа) разрешена и при наличии правил: `moveKeyRules` в `actions/admin.ts` переписывает правила под нового владельца (командный — всё в его команду, личный — в личные правила, общий — без изменений), сервисы и модели сохраняются. Удаление ключа удаляет его правила в одной транзакции; страница ключа заранее показывает, какие слоты останутся без ключа.
- Настройка: `/users` (список + форма «Добавить сотрудника» `components/users/NewUserForm.tsx`: админ сам задаёт логин и пароль, профиль прав и команды; приглашений и писем нет) → `/users/[id]` (права `PermissionsFields`, команды/лидер, логин, роль, пароль). Только админ меняет права. Логин — почта или короткое имя (`LOGIN_RE`, `normalizeLogin` в `lib/auth.ts`), хранится в `User.email`; поля `inviteToken/inviteExpires` в схеме остались, но не используются.
- Ключ бывает личным (`ownerId`), командным (`teamId`) или общим. Командный ключ видят участники команды, назначается только правилам своей команды (на странице ключа команда фиксирована). Форма «чей ключ» — `components/KeyOwnerFields.tsx` (`owner` = personal | team:<id> | shared); сменить владельца можно только у ключа без правил. Правила: `createBinding` проверяет область (`assignScope`) и совместимость ключа (`keyFitsRule`); `BindingForm` получает `can={{ meId, myTeamIds, assign }}` и показывает только подходящие ключи.
