# Zewex Tools — заметки для Claude

Внутренний портал инструментов на https://zewex.tools. Общение с владельцем на русском, он не технический: команды давать пошагово.

## Стек и структура
- Next.js 15 (App Router, `output: standalone`), React 19, Tailwind 4, Prisma 6, MariaDB.
- `src/lib/resolve.ts` — выбор правила для слота (USER_PROJECT → TEAM_PROJECT → PROJECT → TEAM → GLOBAL). Третий аргумент `teamId` — команда работы (команда сайта/прогона): уровни «команда» смотрят только её правила, деньги списываются строго с её ключей, даже если сотрудник состоит в нескольких командах (инцидент 2026-10-22: сайт WexOra, ключи Zewex). Все инструменты передают `ctx.teamId` в `resolveSlot`; `runSlot` без `pre` берёт `meta.teamId`.
- Резерв денег под прогон пинов: `createRun` считает `runEstimate` по команде сайта и пишет `RunSettings.estimate` (`RunReservation`: оценка по ключам). `activeReservations()` в `lib/pins/runs/estimate.ts` — у незавершённых прогонов (QUEUED/RUNNING/WAITING_MODERATION/BLOCKED) оценка по ключу минус потраченное по журналу = «в работе»; оценка следующего прогона показывает «на счёте / в работе / свободно» и `risks` («попросите администратора пополнить»), риски дублируются в предупреждения запуска. Остаток OpenRouter/laozhang/DataForSEO сотруднику — по его ключу (`keyRemaining` в `lib/balances.ts`). Рядом с ключом везде подпись, чей он (`keyOwnerLabel`: имя команды / «личный · Имя» / «общий»): оценка прогона, окно балансов сотрудника и админа.
- Плашка «Сервер» в шапке рядом с балансами (`components/HeaderServer.tsx`, `GET /api/server-status`, `lib/serverStatus.ts`): свободное место на `/`, загрузка процессора за 0,5 с по `/proc/stat` и средняя очередь задач, память по MemAvailable; кэш 15 с, опрос раз в 30 с; видят все вошедшие; вывод простыми словами (`verdict`).
- `src/lib/adapters.ts` — вызовы провайдеров (OpenAI-совместимые, DataForSEO, SerpAPI); `src/lib/run.ts` — прокси + журнал расхода.
- `src/actions/*.ts` — все мутации (server actions), формы через `components/ActionForm.tsx`.
- `prisma/seed.mjs` — провайдеры, модели Perplexity, разделы (идемпотентен).
- Tailwind 4: нельзя `@apply` своих классов, только встроенные утилиты.
- Свои классы в `globals.css` (`.input`, `.btn*`, `.badge`, `.menu`, `.kpi*`, `.tab`, `.table td/th`, `.table-wrap`) лежат вне `@layer`: утилита на том же элементе их свойство не перебивает, перекрывать только с `!` (`!whitespace-normal`, `sm:!w-[340px]`, `lg:!hidden`). Мобильная вёрстка (телефон 360–390 px): правила и итоги аудита — `docs/mobile-audit-2026-10-24.md` (поля 16px на телефоне, `.col-sm`/`.col-md` для колонок таблиц, `.popover` для окон из шапки, без `sticky top-0` под шапкой портала, действия по наведению дублировать для `hover:none`).
- Длинные списки и пояснения не выводить целиком: `ShowMore` / `ShowMoreRows` (`components/ui/ShowMore.tsx`, первые N + «Показать ещё», строки таблицы — внутри `<tbody>`), `Fold` (свёрнутый блок с итогом в заголовке) и `More` (одна строка + «Подробнее») в `components/ui/Fold.tsx`. `Fold`/`More` — это `<details>`: не класть в `PageHeader subtitle`, `Card description` и любой `<p>` (ошибка гидратации), только отдельным блоком.

## Сборка и деплой
Рабочее место — Windows (`D:\Projects\zewex-tools`, Git Bash), Node локально не нужен: только редактируем, собираем на сервере.
- Деплой одной командой: `bash deploy/deploy.sh` (tar по ssh во временную папку → rsync --delete на сервере → npm install → prisma db push → seed → build → systemd + nginx). Локально нужны только ssh и tar, rsync не нужен. Скрипт отказывает, если в файлах есть CRLF; LF закреплён `.gitattributes` (`eol=lf`) и локально `core.autocrlf false`, `core.filemode false`.
- Один деплой за раз (инциденты 2026-10-22 и 2026-10-24: второй деплой рвал `npm ci` под чужим `next build`, портал отдавал 502). Вся серверная часть `deploy.sh` (загрузка, rsync, бэкап, npm ci, prisma, seed, build, перезапуск) идёт ОДНОЙ ssh-сессией под `flock` на `/var/lock/zewex-deploy.lock`; второй запуск пишет «жду окончания другого деплоя…» и ждёт, через 15 мин выходит с кодом 2. Тот же lock берёт аварийная пересборка `/root/zewex-rebuild.sh`. Под lock скрипт ещё ждёт процессы старых версий без блокировки (`npm ci|install`, `next build`, `rsync -a --delete`, `zewex-backup-db`). Не обходить ожидание и не убивать чужой деплой.
- npm 11.19+ на сервере не запускает install-скрипты пакетов без одобрения: `prisma`, `@prisma/*`, `esbuild` перечислены в `allowScripts` в `package.json` (2026-10-22 деплой падал на `npx prisma db push`: prisma не ставился). При смене версий этих пакетов обновить ключи `allowScripts` (`npm install-scripts ls` на сервере покажет, что не одобрено).
- Проверка типов на сервере: `ssh -i ~/.ssh/fastvps_ed25519 root@159.69.234.194 'cd /var/www/zewex_tools_usr/data/app && sudo -u zewex_tools_usr npx tsc --noEmit'`.
- Логи: `journalctl -u zewex-tools -n 100`. Сервис слушает 127.0.0.1:3100.
- Секреты только в `.env` на сервере (не в git). Никогда не печатать APP_ENCRYPTION_KEY и пароли в чат.
- Репозиторий: `git@github.com:netrebich1/zewex.tools.git`, ветка `main`, пуш через deploy key.

## Pinterest Pins (сервис пинов) и воркер
- Страницы `src/app/(app)/pinterest/pins/*`, действия `src/actions/pins.ts`, библиотеки `src/lib/pins/*` (ai, stages, prompts, plan, texts, wp, schedule, export, canvas). Рецепт сайта и константы — `src/lib/pins/types.ts`.
- Фоновая работа только в воркере `worker/` (systemd `zewex-worker`, `tsx worker/index.ts`): очередь `PinJob`, этапы `worker/stages/*`, реестр `worker/stages/index.ts` — при правках проверять, что все этапы зарегистрированы.
- Чужой домен в ссылках прогона (инцидент 2026-10-16: статьи zorvianix.com запущены в сайт my-home-ideas.com): `lib/pins/siteDomains.ts` (`siteDomains` из имени сайта, `baseUrl`/`linkDomain` доступа и рецепта; `foreignHosts`). Форма нового прогона показывает красное предупреждение с доменами и обязательной галочкой `foreignOk`, `launchRun` без неё отказывает. `parseUrls` считает строку без точки в хосте («url», «pulish») ошибкой. Перенос прогона в другой сайт: `scripts/pins/move-run.ts <runId> <toSiteId> --start=… [--drop-sitename=…] [--delete-old-media] [--apply]` (резервная копия в `pins/runs/<id>/move-backup-*.json`, доски по теме, тексты/загрузка/расписание заново через этап texts; удаление из старой медиатеки — `deleteMedia` в `wp/client.ts`).
- Выбор фото для Canvas (2026-10-16): один раз на статью `choiceFor` в `worker/stages/canvas.ts` — кандидаты равномерно по статье (`spreadIndices`, число = фото всех Canvas-пинов статьи + 2, от 6 до 10: `candidateCount` в `canvas/photoPick.ts`), ОДИН сравнительный вызов `rankPhotos` (`canvas/subject.ts`, text_fast, json, ~$0.0011, кэш `pins/photos/rank-<sha1>.json`) ставит оценки 1–10 и флаги, `assignPhotos` раздаёт лучшие без повторов между пинами и без соседних кадров. Рамки объектов — по-прежнему `subjectBoxFor` только для выбранных фото: совмещать детекцию с оценкой в одном запросе НЕЛЬЗЯ (рамки становятся «на весь кадр»). Оценки пина — `styleParams.photoScores`. Тест A/B: `scripts/pins/photo-score-test.ts <out> <runId>`.
- ИИ-стили (`src/data/pins/ai-styles.json`): у стиля может быть `niches` (decor, interior…) — фильтр «Ниша» в `AiStylePicker`, подписи `STYLE_NICHE_LABELS` в `prompts/aiStyles.ts`. Новогодняя линия для декора/интерьера: 12 направлений × 3 подачи (`ny-decor-*`, категория newyear), добавляются `scripts/pins/add-newyear-decor-styles.py` (идемпотентно). Примеры: `scripts/pins/gen-style-examples.ts --category=newyear --styles=<база> --keyword=… --niche=decor --season=winter` (≈$0.04 за картинку medium).
- Canvas v8 (2026-10-15): `StyleSpec.title` умеет `minSize/maxSize/leading` (постер до 200 px), `outline` (stroke/echo/hollow), `shadow`, `emphasis` (часть слов крупнее/другим шрифтом/цветом, в т.ч. рукописным `fonts.script`; при 7+ словах отключается), `align: left` работает; `photo: {style: polaroid|card, tone: duotone|mono|warm, shape: arch, overlap}`, `ringBadge`, `rule`, `grain` рисуется, `color: photo-tint-dark`, `plate-glass-*` = размытое стекло (`host.snapshot`). Всё это `CanvasRecipe.fx` (`toRecipe`). Зона `middle` — заголовок между рядами фото. Наборы шрифтов несут `scripts` (латинские наборы не идут на кириллицу: `toRecipe(spec, seed, n, {script})`, воркер передаёт `scriptForLanguage`) и `leading`. Свои стили: 20 `zx:*` + 22 `zx27:*` в `curated.ts`; `seedCuratedStyles` обновляет существующие строки каталога при изменении спецификации в коде (превью сбрасывается, утверждение сохраняется) — запускается кнопкой «Обновить превью» (harvest). Хуки Canvas: лимит 44 знака, повисшие предлоги снимаются, резаные хуки идут последними. Отладка новых стилей без базы: `render-style.ts <out> x --spec=<json> --title="…"`.
- Canvas рендерится на сервере (`@napi-rs/canvas`), шрифты в `storage/pins/fonts` (скрипт `scripts/pins/fetch-fonts.mjs`). Каталог стилей: `canvas/catalog.ts` (сбор из легаси + свои стили `canvas/curated.ts` + сочные палитры `canvas/paletteLibrary.ts` + наборы шрифтов `canvas/fontSets.ts`; у стиля 1–4 палитры и до 4 альтернативных наборов шрифтов, seed выбирает; старые строки каталога догоняются `upgradeCatalogSpecs` в `previews` при harvest). Профиль акцента для обрезки (`crop.ts`) задаётся в `worker/stages/canvas.ts` через `guessAccent(ниша, ключ)`. Кадрирование фото: рамка главного объекта от модели со зрением (`canvas/subject.ts`, слот `text_fast` = gemini-2.5-flash, формат детекции `box_2d` 0–1000 БЕЗ json-режима — в json-режиме Gemini отдаёт рамку на весь кадр; кэш `pins/photos/<sha1>.subject.json`, ~$0.0007/фото), `drawSmartCover({subject})` накрывает рамку и держит её верх, если не влезает; без рамки — карта энергии как в легаси (центрирование по боксу акцента). Перерисовать существующий пин текущим кодом: `scripts/pins/render-item.ts <outDir> <itemId…>` в `/root/zewex-check`. Отладочный рендер без базы изменений: `scripts/pins/render-style.ts` + `scripts/pins/contact-sheet.mjs` (запускать в `/root/zewex-check` с `PINS_STORAGE_DIR` на копию). Файлы сервиса: `/var/www/zewex_tools_usr/data/storage/pins`, отдаются nginx как `/files/`.
- Проверка типов воркера: `npx tsc --noEmit -p tsconfig.worker.json`. Без деплоя проверять в копии `/root/zewex-check` на сервере.
- Три уровня настроек. Система `/sites` (`SiteAccess` + `SiteAccessTeam` доп. команды + `SiteAccessViewer` видимость сотрудникам; проверки — `src/lib/sites/access.ts`: `canAccessPinSite`, `pinSiteWhere`, `pinRunWhere`, `canSeeAccess`; `canAccessTeam` только для командных сущностей). Право «Сайты» у сотрудника: `team` / `system` / `all`; `system` = все сайты только в разделе `/sites` — страницы `/sites/*` и действия с них (`saveSiteAccess`, `testSiteAccess`, `setSiteToolActive`, `enable*ForSite`) берут `forSitesTab(me)` из `permissions.ts`, который на время запроса превращает `system` в `all`; в инструментах такой сотрудник видит только свои сайты, и при сохранении сайта он сам в «Кто видит» не добавляется.
- Активная команда: `Session.activeTeamId` (действие `setActiveTeam` в `actions/viewAs.ts`, переключатель `TeamSwitch`/`TeamMenuItems` в шапке — у не-админа с двумя и более командами, в том числе у главного админа в режиме сотрудника). `teamScope` в `lib/auth.ts` сужает `me.teamIds`/`me.leadTeamIds` до активной команды, поэтому все проверки по командам автоматически видят только её; `me.teams` — полный список для шапки. «Все» (null) — как раньше. Балансы в шапке (`/api/balances/mine` → `myKeyBalances(..., me.teamIds)`) считаются по активной команде; `HeaderBalances` в `Shell` получает `key={activeTeamId}`, чтобы перезапросить при смене. Сервис `/pinterest/pins/sites/[id]?tab=settings` (`PinsSiteSettings`: имя, ниша, доски, наборы ИИ, Canvas-стили, Pinora, язык, аудитория, цвет, домен ссылок — в `PinSite.recipe`). Прогон (`PinRun.settings`): источник статей `pages`, mix, photosMode, photoLinkPercent, проценты текстов, numberSource, schedule, multiBoard — форма `RecipeFields scope="run"`, значения по умолчанию из последнего прогона сайта (`runDefaultsFrom`). `recipeFromForm` меняет только присланные группы полей (маркеры `setsPresent`, `multiBoardPresent`, `pagesSkipUsedPresent`).

Поля — `components/pins/PagesSourceFields.tsx` (шаг 3 нового прогона), подбор при запуске без ссылок — `sitePostsBySource` в `lib/pins/wp/posts.ts` из `launchRun`.
- Лимит сайта: `pinsPerDay` — пины ЭТОГО прогона в день; пины других прогонов на те же даты плюсуются, общий потолок 100/день на сайт (`MAX_PINS_PER_DAY`) жёсткий. Лишнее уходит на ближайшие свободные дни; `scheduleItems` сравнивает с раскладкой без лимита (`ignoreSiteLimit`) и отдаёт `limitReport`, этап `schedule` пишет `settings.scheduleReport`, `explainSchedule` показывает жёлтую плашку «перенесено N и почему». Выгрузка дня — один файл на сайт по всем прогонам; все сайты на сегодня — `todayAllZip`, `GET /api/pins/export/today`, выделенная ссылка в `PinsNav`.
- Расписание прогона (`schedule/plan.ts`, `scheduleItems`): два режима `schedule.dailyMode` — `fixed` (строго pinsPerDay в день, окно растёт само) и `dates` (равномерно от startFrom до lastDate, потолок 100/день, остаток после lastDate). День наполняется до нормы в три прохода: желаемая дата наступила и предпочтения статьи соблюдены → будущие подтягиваем вперёд → ослабляем «со статьи в день»; порядок пинов внутри статьи не ломается. Особые годы прогона `text.yearRules` (галочка «Другой год для отдельных тем», `YearRulesFields.tsx`): слово в ключе/заголовке/H1/теме статьи → год правила (`pinYearFor`); выключенные правила сохраняются, но не действуют.
- Фото статьи: `Recipe.photosMode` = `auto` (по умолчанию; старое "all" читается как auto) | `sections` | `featured_only`; `featuredOnlyFor(mode, page.niche, site.niche)` — в auto кулинарные статьи (`niche = cooking`) берут только миниатюру. Менять сайт (доступ, команды, видимость, подключение инструментов) — `canEditAccess`: админ, тот, кто управляет командой-владельцем (лидер), или отмеченный сотрудник команды-владельца; остальным страница сайта показывает плашку без формы. `saveSiteAccess` сохраняет команды и сотрудников, которых форма пользователю не показывает (он в них не состоит). `saveSiteAccess` оставляет автора в списке видящих (кроме админа/лидера). Прогоны и модерация наследуют видимость сайта. Проверка «что видит сотрудник» — скрипт по образцу из истории (`pinSiteWhere`, `pinRunWhere`, `moderationCounts` с собранным `CurrentUser`).

- Оценка стоимости прогона до запуска (2026-10-22): `lib/pins/runs/estimate.ts` — `costRates()` (средние по DONE-прогонам за 60 дней из UsageLog по слотам: image_main за ИИ-пин, text_main за любой пин, text_fast за статью; по провайдерам, кэш 10 мин) и `runEstimate(me, {pages, mix})` — ключ/провайдер слота через `resolveSlot`, остаток: OpenRouter/laozhang из `providerBalances` (кто видит балансы), OpenAI — ручной остаток ключа `manualBalances`; `enough` = остаток ≥ 1,2×. API `GET /api/pins/estimate?pages&ai&photos&canvas&pinora`, блок `components/pins/RunCostEstimate.tsx` в форме нового прогона читает `mixAi…` из формы, статьи считает `NewRunForm` (ссылки / выбранные / лимит фильтра).
- Лимит провайдера (429 TPM/RPM, 2026-10-22): семафор ключа `ai/limiter.ts` раздаёт места по кругу между владельцами (`owner` = id прогона), после «rate limit» `pauseKey` ставит ключ на паузу для всех прогонов (60 с, ×2 до 5 мин, сброс `keyOk` при успехе). Пин при `rate_limited` повторяется до 10 раз с паузой 1…10 мин (`RATE_LIMIT_MAX_ATTEMPTS`, `rateLimitDelayMs` в `ai/errors.ts`; прочие transient — 5 раз, ≤60 с). Задача этапа при `retryLater` засыпает до ближайшего `nextRetryAt` (`deferredDelayMs` в `worker/runner.ts`) и сбрасывает `attempts` (`releaseJob(..., {resetAttempts})`), чтобы ожидание не считалось сбоями. Сводка «в работе / осталось символов / хватит на N статей» — `lib/deepl/keys.ts` `keysSummary`, полоска `components/deepl/DeeplHeader.tsx` на всех страницах. ## Трафик сайтов (раздел Аналитика, проект `analytics`) — Google Analytics 4
- Кабинет поверх GA4 для всех Google-аккаунтов владельца: `/analytics` (обзор: KPI, график, таблица сайтов, каналы/страны/устройства, часы), `/analytics/sites/[id]` (сайт: вкладки страницы/источники/география/устройства/часы), `/analytics/pages` (страницы всех сайтов: поиск по адресу и заголовку, фильтр сайт/группа, сортировка рост/падение), `/analytics/settings` (аккаунты, переключатели сайтов, группы). Инструкция по Google Cloud — `docs/analytics/README.md`.
- Аккаунты Google — внутри инструмента (`GaAccount`: OAuth refresh token или JSON сервисного аккаунта, зашифрованы), не в общем разделе «Ключи». OAuth: `GOOGLE_OAUTH_CLIENT_ID/SECRET` в `.env`, `/api/analytics/oauth/{start,callback}` (state в cookie), scope analytics.readonly. Видимость: автор аккаунта + ADMIN (`accountWhere`/`propertyWhere`/`groupWhere` в `lib/analytics/access.ts`, ими же проверяются все действия); на экранах просмотра лидер команды видит ещё сайты сотрудников (не админов) своих команд — `propertyViewWhere` (`visibleSites`, страница сайта, realtime).
- Данные живут в своей базе: `GaDaily` (итоги дня), `GaHourly`, `GaPageDaily` (топ 1000 страниц/день, ключ sha1 пути, `normalizePath` без хвостового слэша), `GaDimDaily` (kind: channel/source/country/device/referrer). Синхронизация — воркер `worker/analytics.ts` → `lib/analytics/sync.ts` `syncProperty`: каждый час перечитывает 3 дня, историю докачивает порциями (`BACKFILL_DAYS` в `types.ts`: 400/400/90/120 дней; страницы по 10 дней за проход), `syncState.done` — история загружена. Ошибка авторизации → `GaAccount.status=ERROR`, сайты аккаунта не синхронизируются до переподключения. Отказы = 1 − engaged/sessions, время = engagementSec/sessions (`derive` в `query.ts`), конверсии = `keyEvents`.
- Период из адреса (`lib/analytics/period.ts` `parseRange`: `p`, `from`, `to`, `cmp` prev/year/none, `g` hour/day/week/month, `m`), «сегодня» — пояс свойства или `GA_DEFAULT_TZ` (Europe/Kyiv). Выборки — `query.ts` (raw SQL, `CAST(... AS DOUBLE)`), сравнение выравнивается по индексу. Realtime («сейчас на сайте») — `/api/analytics/realtime?ids=`, кэш минута. CSV — `/api/analytics/export?kind=sites|pages`. Графики: цвета `--viz-1`/`--viz-prev` в `globals.css`, одна ось, сравнение пунктиром (`TimeChart.tsx`).

У сотрудника набор `Permissions` в `User.permissions` (JSON, null = по умолчанию): `usage` own/team/all, `keysView` none/own/team/all, `keysCreate` none/personal/team/all, `keysAssign` none/team/all, `teams` view/manage/all, `providers` none/view/manage, `sites` team/all, `balances`, `users` none/view. Всё в `src/lib/permissions.ts` (типы, профили «Сотрудник / Лидер команды / Менеджер», `PERMISSION_FIELDS` для формы, чистые проверки `canViewKey`, `keyWhere`, `canManageKey`, `assignScope`, `canAssignGlobal`, `keyFitsRule`, `canDeleteBinding`, `canManageTeam`, `usageWhere`, `seesAllSites`, …). `CurrentUser.perms` считается в `getCurrentUser`; меню `Shell` и `/api/balances` фильтруются по правам. Лидер команды (`TeamMember.role = LEAD`) всегда имеет уровень «команда» в своей команде поверх личных прав.
- Инструменты сотрудника: `Permissions.tools` = `"all"` или список slug проектов (по умолчанию пусто — ни одного), галочки `components/users/ToolsAccessFields.tsx` на `/users` и `/users/[id]`. Закрытие в одном месте: middleware кладёт путь запроса в заголовок `x-zx-path` (`lib/requestPath.ts`), `requireUser`/`getCurrentUser` в `lib/auth.ts` по `Project.url` и `/api/<slug>` определяют инструмент и не пускают (`/?denied=1` или 401). Новому инструменту нужен `url` в сиде и API под `/api/<slug>/…`, тогда он закрывается сам. Плюс `toolWhere` на главной, `canUseTool` в `/projects/[slug]` и `/api/run`. Разделы «Команды» и «Расход» у сотрудника по умолчанию скрыты (`teams: "none"`, `usage: "none"`; `canViewTeams`, `teamWhere`, `canViewUsage`), лидер свою команду и её расход видит.
- Главные админы (владелец из `ALLOWED_REGISTRATION_EMAILS` всегда + `User.superAdmin`, ставит только владелец на `/users/[id]`): переключатель «Админ / Сотрудник» у аватарки (`Session.memberView` → роль MEMBER, его команды, права из его `User.permissions`; не сохранены — по умолчанию со всеми инструментами) и вход в кабинет любого активного сотрудника (`Session.actAsUserId`, меню под аватаркой или кнопка на `/users/[id]`). Всё в `getCurrentUser` (`lib/auth.ts`), поэтому подмена действует во всех страницах, действиях и API; настоящий вошедший — `realSession()`. Флаги живут в сессии главного админа: вернуться может только он, у сотрудника ничего не меняется; в кабинет главного админа войти нельзя. Действия — `actions/viewAs.ts`, UI — `components/ViewAs.tsx`, цвет шапки — `.view-member` (синий) / `.view-as` (фиолетовый) в `globals.css`. Действия в чужом кабинете пишутся в журнал расхода от имени сотрудника; входы и выходы — строка `[view-as]` в `journalctl -u zewex-tools`.
- Остаток на ключе вручную (OpenAI и другие LLM без баланса по API): `ApiKey.balanceUsd/balanceAt`, действие `setKeyBalance` (вписать заново / прибавить пополнение), расчёт `manualBalances` в `lib/balances.ts` = сумма − расход по `UsageLog` через ключ с момента ввода (все инструменты и команды; стоимость — оценка по ценам моделей). Балансы в шапке — право `balances`: `none` / `own` (по умолчанию: только ключи, на которых сотрудник работает по правилам своих команд или личным в открытых ему инструментах; общие ключи сервиса уровня PROJECT/GLOBAL не показываются) / `all` (все провайдеры, как у админа): `myKeyBalances` → `/api/balances/mine` → `HeaderBalances mine`.
- Смена владельца ключа («Чей ключ» на странице ключа) разрешена и при наличии правил: `moveKeyRules` в `actions/admin.ts` переписывает правила под нового владельца (командный — всё в его команду, личный — в личные правила, общий — без изменений), сервисы и модели сохраняются. Удаление ключа удаляет его правила в одной транзакции; страница ключа заранее показывает, какие слоты останутся без ключа.
- Настройка: `/users` (список + форма «Добавить сотрудника» `components/users/NewUserForm.tsx`: админ сам задаёт логин и пароль, профиль прав и команды; приглашений и писем нет) → `/users/[id]` (права `PermissionsFields`, команды/лидер, логин, роль, пароль). Только админ меняет права. Логин — почта или короткое имя (`LOGIN_RE`, `normalizeLogin` в `lib/auth.ts`), хранится в `User.email`; поля `inviteToken/inviteExpires` в схеме остались, но не используются.
- Ключ бывает личным (`ownerId`), командным (`teamId`) или общим. Командный ключ видят участники команды, назначается только правилам своей команды (на странице ключа команда фиксирована). Форма «чей ключ» — `components/KeyOwnerFields.tsx` (`owner` = personal | team:<id> | shared); сменить владельца можно только у ключа без правил. Правила: `createBinding` проверяет область (`assignScope`) и совместимость ключа (`keyFitsRule`); `BindingForm` получает `can={{ meId, myTeamIds, assign }}` и показывает только подходящие ключи.
